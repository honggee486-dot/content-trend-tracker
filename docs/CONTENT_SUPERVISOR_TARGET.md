# 콘텐츠 기회 레이더 + 감독형 반자동 제작 목표

## 목표

`content-trend-tracker`의 장기 사용 방식은 단순히 이미 많이 언급된 트렌드를 나열하거나 사용자가 제작 단계를 반복 조작하는 도구가 아니다.

프로그램이 **앞으로 검색될 가능성이 높고 아직 정보성 콘텐츠 공급이 부족한 소재를 조기에 발견**하고,
관찰·판단·글감 승격·작성·검수·사실 확인·이미지 준비·발행 준비를 대부분 수행하며,
사용자는 핵심 선택과 최종 공개 판단에 집중하는 **콘텐츠 기회 레이더 + 감독형 반자동 제작 시스템**으로 한다.

정상 흐름:

```text
외부 신호 수집
→ 시간별 관측·확산 추적
→ 수요 / 공급 / 포화도 / 예상 수명 계산
→ Watchlist
→ 🔥 급상승 / 🟠 초기 신호 / 🟢 정보성 기회 / ⚪ 포화·종료
→ 예상 검색 의도 생성·근거 검증
→ 작성 가치가 있는 소재만 기존 글감 흐름으로 승격
→ 추천 글감 선택
→ 검증 점수 1순위 주제 방향 기본 선택
→ 자동/수동 작성 추천 확인 및 필요 시 변경
→ 기존 작성 경로로 1차 글 작성
→ 기본 JSON·출처 검사
→ Luna High 텍스트 품질 감사 1회
→ 필요 시 기존 작성 모델이 Luna 수정 요청만 반영
→ 최종 출처·사실·JSON 검사
→ 최종 텍스트 확정
→ 최종 글 기준 이미지 전략 재계획
→ 공식 화면 캡처 / 0원 생성 / 검증 무료 자산 / 이미지 없음
→ 이미지 후처리·본문 배치
→ 대상 블로그 자동 배정
→ 플랫폼별 임시저장 또는 안전한 편집기 준비
→ 사용자 최종 확인
→ 발행 / 수정 / 삭제·보류
```

## 콘텐츠 기회 레이더의 판단 원칙

단순한 현재 언급량이나 검색 결과 총량만으로 좋은 글감을 판단하지 않는다.

우선 보는 값:

- 최초·최근 포착 시각과 관측 이력
- 관심 증가 속도 `velocity`
- 증가 속도의 변화 `acceleration`
- 여러 출처에서 나타나는 순서와 시간차
- 검색·관심 수요
- 최근 관련 콘텐츠 공급량과 증가 속도
- 공급 대비 수요 기회
- `saturation`
- `expected_lifetime`
- 정보성 질문으로 확장될 가능성
- 공식·신뢰 가능한 근거 확보 가능성

같은 URL·외부 ID가 반복 수집될 때 원문 행을 무한 추가하지 않는 기존 멱등성 계약을 유지한다.
원문 게시 시각을 재수집 시각으로 덮어쓰지 않고 관측 이력은 별도로 보존한다.

## Watchlist 상태 계약

기본 상태는 네 개로 유지한다.

- 🔥 **급상승** — 몇 시간 안에 판단해야 하는 소재
- 🟠 **초기 신호** — 아직 작지만 증가 속도가 높아 계속 관찰할 소재
- 🟢 **정보성 기회** — 폭발적이지 않아도 검색 수요 대비 좋은 정보성 콘텐츠가 부족한 소재
- ⚪ **포화/종료** — 이미 콘텐츠가 많거나 관심이 꺾인 소재

상태와 행동 권장은 분리한다.

예:

```text
🔥 급상승      → 지금 작성
🟠 초기 신호   → 계속 관찰
🟢 정보성 기회 → 지금 작성
⚪ 포화/종료   → 종료
```

이모지는 장식이 아니라 운영 상태를 빠르게 구분하는 일관된 배지로 사용한다.

## 예상 검색 의도

현재 사건·키워드를 그대로 다시 쓰는 것에 그치지 않고 사람들이 곧 검색할 가능성이 있는 정보성 질문을 만든다.

예:

```text
지원 정책 발표
→ 대상은 누구인가?
→ 언제부터 신청하는가?
→ 신청방법은 무엇인가?
→ 소득·자산 기준은 무엇인가?
→ 필요한 서류는 무엇인가?
→ 기존 제도와 무엇이 다른가?
```

AI는 질문 후보를 생성할 수 있지만 새 사실·수치·URL·source_id를 임의로 만들지 않는다.
글감 승격 전 실제 외부 신호와 공식·신뢰 가능한 근거로 다시 검증한다.

## 사용자가 맡는 일

정상 케이스의 반복 작업은 다음을 중심으로 줄인다.

1. 🔥/🟠/🟢/⚪ 상태와 근거를 보고 지금 작성할지 계속 관찰할지 판단
2. 승격된 추천 글감 중 실제로 쓸 주제 선택
3. 기본 1순위 주제 방향을 그대로 쓰거나 변경
4. 자동/수동 작성 추천을 그대로 쓰거나 변경
5. 준비된 최종 글과 이미지를 확인해 발행·수정·삭제·보류

자료 수집, 관측 이력 누적, 기회 점수 계산, 군집, 글감 평가, 근거 정리, 기본 방향 선정, 요청서 작성,
1차 결과 검사, Luna 감사, 수정 요청 전달, 최종 사실 확인, 이미지 획득,
초안 저장, 블로그 배정과 플랫폼별 준비는 가능한 범위에서 프로그램이 처리한다.

## UI 목표

전체 화면은 기능을 세로로 길게 나열하는 구조보다 **운영 콘솔**로 보이게 한다.

기본 레이아웃:

```text
좌측 고정 메뉴
→ 페이지별 상단 미니 대시보드
→ 필터·빠른 액션
→ 상세 목록/작업 영역
→ 필요 시 접힌 로그·진단
```

좌측 메뉴는 작업 단계 기준으로 구성한다.

- 대시보드
- 기회 레이더
- 트렌드·군집
- 글감·주제 방향
- 작성
- 검수
- 이미지
- 발행 준비
- 로그·진단
- 설정

상단 미니 대시보드는 현재 페이지에서 바로 판단할 핵심 수치만 보여준다.
기회 레이더 화면에는 최소 다음 네 상태 카드를 둔다.

```text
🔥 급상승
🟠 초기 신호
🟢 정보성 기회
⚪ 포화/종료
```

상세 목록에는 가능한 범위에서 소재, 상태, 수요 속도, 공급량, 포화도, 예상 수명, 추천 검색 의도, 권장 행동을 표시한다.
기존 기능을 삭제하거나 중복 구현하지 않고 단계적으로 현재 화면 구조를 재배치한다.

## 자동화 경계

자동화 수준을 높여도 다음을 유지한다.

- 자동 로그인 금지
- 브라우저 쿠키·세션 토큰·기존 프로필 직접 수집/저장 금지
- CAPTCHA 우회 금지
- 사용자 승인 없는 최종 공개 게시 금지
- 실제 비용이 발생할 수 있는 AI 모델의 자동 사용 금지
- 플랫폼이 공식 지원하지 않는 비공개 작성 API 추측 사용 금지
- 실제 DB·Secret·개인 데이터 보호

플랫폼별 임시저장은 공식 API 또는 현재 프로젝트의 안전한 사용자 보조 방식으로 가능할 때만 자동화한다.
지원되지 않으면 편집기 입력 준비까지 자동화하고 최종 저장/공개는 사용자가 수행한다.

## 단계별 구현 순서

### 1. 현재 실행 기반 검증

현재 자동/수동 작성, Luna High, 대표 이미지, 공개 공식 페이지 캡처 기반의 테스트·하네스 선택이 실제 코드와 맞는지 먼저 정리한다.
하네스에서는 실제 외부 API·Secret·브라우저 스모크를 사용하지 않는다.
실제 Chrome/Edge 또는 외부 모델 품질은 필요한 시점에 별도 실환경 검증으로 확인한다.

### 2. 콘텐츠 기회 레이더 데이터 계약

관측 이력, velocity, acceleration, 수요, 공급, saturation, expected_lifetime, 출처 확산 순서를 추가형 호환 계약으로 저장·계산한다.

### 3. Watchlist와 상태 판정

🔥 급상승 / 🟠 초기 신호 / 🟢 정보성 기회 / ⚪ 포화·종료 상태와 별도 행동 권장을 계산한다.

### 4. 예상 검색 의도 생성·검증

현재 신호에서 파생되는 정보성 검색 질문 후보를 만들고 실제 근거와 대조한다.

### 5. 기존 글감 승격 흐름 연결

작성 가치가 확인된 Watchlist 소재만 기존 군집·글감·주제 방향 파이프라인으로 승격한다.

### 6. 운영 콘솔 UI 개편

2~5단계의 데이터를 실제로 판단할 수 있도록 좌측 메뉴, 상단 요약 카드, 필터, 상세 영역, 상태 배지를 연결한다.

2~6단계는 최종적으로 하나의 사용자 기능으로 동작해야 한다. 내부 구현은 검증·롤백 가능한 응집 단위로 나눌 수 있지만 데이터만 만들거나 UI만 바꾸는 반쪽 완료로 끝내지 않는다.

### 7. 자동 작성 → Luna → 최종 검증

자동 작성:

- 공식적으로 허용된 구독형 실행 경로가 안전하게 사용 가능하면 우선 검토
- 불가·한도·일시 실패 시 저장된 0원 API 1~4순위를 사용
- 각 외부 호출 직전 0원 여부 재확인
- 첫 정상 응답에서 종료
- 모두 실패하면 요청서·자료팩을 보존하고 수동 흐름으로 전환

수동 작성:

- 기존 `ChatGPT에서 요청하기 → JSON 가져오기` 흐름 보존
- 특정 모델명을 저장 schema나 UI 필수 계약으로 고정하지 않음

Luna High:

- 사진·캡처·thumbnail은 제외
- 작성자가 아니라 감사자
- 원고를 직접 다시 쓰지 않고 `revision_requests`와 `keep_points`만 반환
- 정상 케이스 글 한 편당 1회만 감사
- `revision_needed`면 기존 작성 모델 수정도 최대 1회

Luna 결과 자체를 사실 검증으로 취급하지 않고 최종 문장을 sources·fact_checks·JSON으로 다시 검사한다.

### 8. 최종 이미지 계층

이미지 계획은 최종 텍스트 확정 뒤 다시 만든다.

우선순위:

1. 공식 화면 자체가 사실 근거에 유용함 → `official_capture`
2. 대표/설명용 이미지가 적합함 → 0원 생성 이미지
3. 라이선스가 명확한 무료 자산이 더 적합함 → `verified_free`
4. 이미지가 의미 있게 기여하지 않음 → 이미지 없음

1차 글쓰기 중 만들어진 image 계획은 최종 실행 계약으로 사용하지 않는다.

### 9. 블로그별 발행 준비

- 블로그 추천·배정 결과 재사용
- Blogger → Tistory → Naver Blog 순으로 실제 지원 범위 검증
- 공식 임시저장 지원 시에만 자동 임시저장
- 아니면 제목·본문·태그·이미지·링크를 안전한 편집기 입력 준비 상태로 만듦
- 최종 공개는 사용자

### 10. 실제 글 E2E 검증

실제 정보성 글을 Blogger, Tistory, Naver Blog에서 각각 최소 1편씩 처리해 전체 감독 흐름을 검증한다.
공통 문제와 플랫폼 고유 문제를 분리하고 앞 단계의 공통 문제는 다음 플랫폼 전에 수정한다.

## 현재 구현 상태

현재 저장소에는 다음 기반이 있다.

- 트렌드 수집·군집·글감 후보와 추천 흐름
- source_items의 최초·최근 재포착 시각과 누적 포착 횟수 기반
- 수집 query별 discovery 원장 기반
- 기존 trend/opportunity/quality/rediscovery 점수 기반
- Gemini 주제 방향과 1순위 기본 선택
- 자동/수동 작성 추천 계약
- AI 요청서 → AI JSON 검사 → draft → fact-check → 발행 보조
- 현재 0원 자동 작성 모델 카탈로그와 1~4순위 설정
- 1시간 model catalog / 24시간 performance lazy refresh
- 호출 직전 0원 여부 재확인 계약
- Luna High 품질 감사 순수 cycle 계약
- 공식 캡처 / 검증 무료 이미지 / 생성 이미지의 이미지 전략 기반
- 격리 Headless Chrome/Edge CDP 공개 페이지 캡처 executor 기반

아직 구현하지 않은 핵심은:

- 시간별 콘텐츠 기회 관측 원장과 속도·가속도 계산
- 수요·공급·포화도·예상 수명 계약
- Watchlist와 🔥/🟠/🟢/⚪ 상태 전이
- 예상 검색 의도 검증과 기존 글감 승격 연결
- 좌측 메뉴 + 상단 미니 대시보드 + 상세 작업 영역의 운영 콘솔 UI
- 자동 작성 → Luna → 최종검증 → 이미지 → 발행 준비의 완전한 실제 cycle 연결

## 완료 기준

일반적인 소재 발견부터 글 한 편 준비까지 다음이 성립해야 한다.

- 단순 인기 총량보다 상승 속도·공급 부족·포화도·예상 수명을 구분함
- 관찰 소재가 Watchlist에서 시간에 따라 상태를 바꿀 수 있음
- 🔥/🟠/🟢/⚪ 상태가 화면에 일관된 배지로 표시됨
- 예상 검색 의도가 실제 근거와 함께 검증됨
- 작성 가치가 있는 소재만 기존 글감 파이프라인으로 승격됨
- 좌측 메뉴 + 상단 요약 + 상세 영역의 운영 콘솔 UI가 동작함
- 사용자가 여러 제작 화면을 순서대로 찾아다닐 필요가 줄어듦
