# 0.10.110 다음 작업 — 블로그 실사용 검증

## 목적

0.10.109 이후에는 기능을 추측해서 더 추가하기보다 실제 블로그를 개설하고 정보성 글을 끝까지 발행하면서 사용 흐름의 불편과 누락을 확인한다. 실제 사용에서 확인된 문제를 우선 수정하고, 근거가 없는 자동화·대규모 기능 추가는 보류한다.

## 실사용 순서

### 0. 사전 확인

1. 로컬 앱이 0.10.109 기준으로 정상 실행되는지 확인한다.
2. 테스트용 문구가 아니라 실제로 남겨둘 정보성 글감을 사용한다.
3. 처음부터 세 플랫폼을 모두 만들지 않는다. 한 플랫폼에서 실제 글 1편을 끝까지 처리하고, 막히는 문제가 있으면 다음 플랫폼으로 넘어가기 전에 먼저 수정한다.
4. 첫 공개 테스트 글은 플랫폼별로 서로 다른 실제 주제를 사용해 동일 글 복제 때문에 생기는 변수를 줄인다.
5. 자동 로그인·쿠키 저장·CAPTCHA 우회·무인 자동 발행은 추가하지 않는다. 로그인과 최종 공개 판단은 사용자가 직접 한다.

### 1. Blogger — 첫 실사용

1. Google 계정으로 Blogger에 로그인한다.
2. 블로그 1개를 만들고 블로그명과 주소를 정한다.
3. content-trend-tracker에서 실제 글감 1개를 고른다.
4. `글감 선택 → 자료팩 → AI 요청서 → AI 결과 입력/검사 → 편집 → 사실 확인 → 발행 보조` 전체 흐름을 실제로 사용한다.
5. Blogger 편집기에 제목·본문·이미지·링크·라벨 등 필요한 값을 넣고 미리보기를 확인한다.
6. 실제 공개할 품질이면 직접 발행한다.
7. 아래 불편 기록 항목을 남긴다.
8. 진행을 막는 문제나 반복 불편이 있으면 Tistory로 넘어가지 말고 먼저 수정한다.

### 2. Tistory — 두 번째 실사용

Blogger 한 편의 전체 흐름이 막힘 없이 완료된 뒤 진행한다.

1. Tistory에 로그인하고 블로그 1개를 개설한다.
2. Blogger와 다른 실제 정보성 글감 1개를 고른다.
3. content-trend-tracker의 동일한 제작 흐름을 끝까지 진행한다.
4. Tistory 편집기에서 제목·본문 서식·이미지·링크·카테고리·태그·미리보기·발행 단계의 불편을 확인한다.
5. 실제 공개할 품질이면 직접 발행한다.
6. Blogger에서 없었던 플랫폼 고유 불편과 공통 반복 불편을 구분해서 기록한다.
7. 진행을 막는 문제나 반복 불편이 있으면 Naver Blog로 넘어가기 전에 먼저 수정한다.

### 3. Naver Blog — 세 번째 실사용

Blogger와 Tistory의 실사용 흐름이 안정된 뒤 진행한다.

1. Naver 계정으로 블로그 1개를 개설한다.
2. 앞의 두 플랫폼과 다른 실제 정보성 글감 1개를 고른다.
3. content-trend-tracker의 제작 흐름을 끝까지 진행한다.
4. Naver 편집기에서 제목·본문 서식·이미지·링크·태그·공개/검색 설정·미리보기·발행 단계의 불편을 확인한다.
5. 실제 공개할 품질이면 직접 발행한다.
6. 플랫폼별 차이 때문에 별도 보조가 필요한지, 공통 기능으로 해결 가능한지 구분한다.

## 불편 기록 기준

문제가 생기면 다음 정보만 남기면 다음 개발 작업의 근거로 사용한다.

- 플랫폼과 현재 단계
- 기대한 동작
- 실제 동작
- 화면 캡처 또는 오류 문구
- 한 번만 생긴 문제인지 반복되는지
- 우회해서 계속 진행할 수 있는지, 진행을 막는지
- 복사·붙여넣기·서식·이미지·태그·사실 확인·발행 기록 중 어디가 불편했는지

## 세 플랫폼 완료 후 판단

세 플랫폼에서 실제 글을 최소 1편씩 발행한 뒤 문제를 다음 순서로 분류한다.

1. 발행을 막는 오류·데이터 손실·상태 꼬임
2. 매번 반복되어 시간이 많이 드는 불편
3. 플랫폼별 서식·이미지·태그 차이
4. 있으면 편하지만 현재 작업을 막지 않는 개선

1~3의 실제 사례를 다음 개발 우선순위로 사용한다. 4는 실사용이 더 누적된 뒤 검토한다. 실제 사례 없이 게시 자동화 범위를 확대하거나 새로운 플랫폼을 추가하지 않는다.

- Tistory 실제 정보성 글 1편 발행 완료
- Naver Blog 실제 정보성 글 1편 발행 완료

## 무료 외부 트렌드 신호 후보 — 실사용 안정화 후 검토

블로그 실사용 검증과 현재 수집·군집 안정화가 끝난 뒤에만 검토한다. 기존 NAVER·Daum·Google Trends·YouTube·Wikimedia와 같은 성격의 신호를 단순히 늘리지 않고, 비용이 들지 않으면서 서로 다른 선행 신호를 주는 출처만 우선한다.

### 1. GDELT — 글로벌 뉴스 확산 신호

- 1순위 후보. 전 세계 뉴스에서 특정 주제의 보도 비중·기사 수·대표 기사 변화를 시간대별로 받아 현재 검색·영상 신호와 다른 `언론 확산 속도`를 보강할 수 있는지 검증한다.
- 처음부터 기사 원문 저장이나 대규모 백필을 하지 않고 최근 짧은 구간의 `TimelineVol`/`TimelineVolRaw` 수준만 읽어 `TrendSignal`로 정규화한다.
- 소규모 무료 검증에서 기존 신호보다 실제 글감 선행 발견이나 신뢰도 보강 효과가 확인될 때만 정식 adapter를 만든다.
- 호출 실패나 응답 지연이 기존 수집 성공을 취소하지 않게 하고 last-good 결과를 보존한다.

### 2. Hacker News 공식 API — AI·개발·스타트업 기술 신호

- 기술 분야에 한정한 2순위 후보. `topstories`·`newstories`의 제목, 점수, 댓글 수와 시간 변화를 이용해 AI·개발도구·보안·스타트업 이슈의 초기 커뮤니티 반응을 보조 신호로 사용할 수 있는지 검증한다.
- 범용 사회·연예 트렌드 점수에는 직접 섞지 않고 `tech` 계열 후보에서만 가중하거나 별도 source label로 유지한다.
- 처음에는 상위/신규 story의 메타데이터만 읽고 댓글 본문 전체 수집이나 사용자 프로필 수집은 하지 않는다.
- API가 무료라는 이유만으로 고빈도 polling하지 않고 적당한 간격·캐시·중복 제거를 사용한다.

### 3. Bluesky 공개 API/Jetstream — 소셜 확산 보조 신호

- 3순위 후보. 공개 읽기 API 또는 Jetstream에서 특정 키워드·주제 언급이 짧은 시간에 늘어나는지 확인해 `소셜 선행 신호`로 쓸 수 있는지 작은 실험으로 검증한다.
- 전체 firehose 영구 저장은 하지 않고 필요한 collection/키워드만 제한적으로 처리한다.
- 단일 Bluesky 이용자층을 전체 대중 관심으로 간주하지 않고 NAVER·Google·YouTube·GDELT 같은 다른 출처와 함께 나타날 때만 보강 신호로 사용한다.
- 공개 API의 rate limit과 public-web 정책을 존중하고, 429 발생 시 backoff하며 수집 실패가 기존 결과를 덮어쓰지 않게 한다.

### 현재 보류

- **Mastodon Trends**: 공개 endpoint는 유용하지만 instance별 편향이 커서 여러 서버를 운영·정규화하는 비용 대비 현재 우선순위는 낮다.
- **OpenAlex**: 연구·과학 신호에는 가치가 있지만 API가 freemium 구조이므로 `완전 무비용 우선` 기준에서는 뒤로 둔다. 과학·AI 연구 글감 비중이 실제로 커질 때 무료 한도 내 별도 검증한다.
- **GitHub REST 검색/이벤트**: 개발 신호는 Hacker News와 일부 겹치고 rate limit·검색 쿼터 관리가 추가되므로 지금은 새 source로 넣지 않는다.

### 채택 순서와 완료 기준

1. GDELT 하나만 소규모로 검증한다.
2. 기존 데이터와 같은 시간축에서 `새로 잡힌 유효 글감`, `중복 신호`, `노이즈`, `수집 지연`, `운영비 0원 유지 여부`를 비교한다.
3. 효과가 명확할 때만 정식 adapter로 승격한다.
4. 그 다음 기술 특화 Hacker News, 소셜 특화 Bluesky 순으로 하나씩 검증한다.
5. 여러 source를 한 번에 추가하지 않는다.

## 후속 기능 후보 — 실사용 안정화 후 검토

Content Trend Tracker에 직접 흡수할 가치가 높고 현재 구현과 중복이 적은 기능만 남긴다. 아래 항목도 현재 블로그 실사용 검증과 수집·군집 안정화보다 우선하지 않는다.

### 1. Data Source Capability / Fallback Matrix

- source가 늘어날수록 각 출처의 역할·무료 여부·coverage·제약·fallback·최근 정상 수집 상태를 한 계약으로 관리할 수 있는지 검토한다.
- 초기에는 새 플랫폼이나 복잡한 Registry를 만들지 않고 기존 adapter metadata/진단 구조를 재사용해 `source_id`, `signal_role`, `free_or_quota`, `coverage`, `priority`, `fallback`, `last_success`, `freshness`, `policy_checked_at` 정도의 최소 matrix부터 검증한다.
- NAVER·Daum·Google Trends·YouTube·Wikimedia에 GDELT·Hacker News·Bluesky 후보까지 늘어날 경우, 각 source가 같은 역할을 중복 수행하지 않고 서로 다른 신호 축을 담당하는지 확인하는 기준으로 사용한다.
- 수집 실패 시 다른 source 성공을 취소하지 않고 last-good 결과를 보존하는 현재 계약을 유지한다.
- 실제 source 추가·장애 대응에서 역할 혼동이나 fallback 판단 문제가 반복될 때 정식 기능으로 승격한다.

### 2. Browser Research Capture → 현재 자료팩 근거 추가

- 현재 페이지에서 `canonical URL → 제목 → 사용자가 선택한 근거 → 메모 → 확인 시각`을 묶어 Content Trend Tracker의 자료 조사 흐름에 제한적으로 추가할 수 있는지 검토한다.
- 현재 Chrome 확장은 `Content Trend Tracker → 블로그 편집기` 입력 보조 역할을 유지하고, 반대 방향의 Research Capture는 사용자가 명시적으로 눌렀을 때만 `Chrome → 현재 글감/자료팩`으로 근거를 전달하는 별도 동작으로 분리한다.
- MVP 후보 데이터는 `source_url`, `page_title`, `selected_text`, `checked_at`, `user_note`, `target_topic/content_pack` 정도로 제한하고 전체 페이지 자동 저장·상시 캡처·로그인 정보·쿠키·브라우저 세션 수집은 하지 않는다.
- 자료팩에 넣기 전 사용자가 대상 글감과 선택 문장을 확인하게 하고, 원문 전체 보존보다 URL·최소 인용·사용자 메모·provenance를 우선한다.
- 블로그 실사용 중 `공식 자료나 기사에서 근거를 찾은 뒤 다시 자료팩에 옮기는 작업`이 반복 불편으로 확인될 때 우선 구현 후보로 승격한다.

### 현재 판단

- 먼저 필요한 것은 새 기능 구현이 아니라 블로그 실사용에서 실제 반복 불편을 확인하는 것이다.
- source가 늘어나 관리 복잡도가 실제로 커지면 **Data Source Capability / Fallback Matrix**를 먼저 검토한다.
- 자료 조사 중 웹 근거를 수동 복사·정리하는 비용이 반복되면 **Browser Research Capture**를 사용자 체감 개선 후보로 우선한다.
- `Meaningful Change Watcher`와 `Resumable Operation`은 가치가 있지만 각각 실제 후속 이슈 추적 필요와 장시간 작업 재시작 문제가 반복된 뒤 다시 평가한다.
