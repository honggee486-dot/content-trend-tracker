# Gemini·프로그램 운영 로그

## 화면 위치

`오늘의 트렌드 → 최근 2단계 군집 작업`의 `배치별 토큰·품질 로그` 바로 아래에 다음 접이식 영역을 표시한다.

- `Gemini 로그 · 최근 100건`
- `프로그램 로그`

오늘의 트렌드에 있던 `Gemini 자동 분석 모델` 선택기는 제거한다. 자동·예약 분석 모델은 설정 화면에서만 변경하며 오늘의 트렌드 작업 버튼은 저장된 설정 모델을 그대로 사용한다.

## Gemini 로그

기존 `gemini_api_calls`에서 최신 100건을 읽는다.

- 호출 시각
- 성공·실패·캐시 상태
- 모델과 기능
- 기능 버전과 시도 번호
- 요청 항목 수
- 입력·출력·사고·전체 토큰
- HTTP 상태와 종료 사유
- 소요 시간과 오류 요약

요청 본문, 응답 본문, API 키는 화면이나 프로그램 로그로 복사하지 않는다.

## 프로그램 로그

추가형 테이블 `program_operation_events`에 다음 운영 이벤트를 기록한다.

- 실제 작업을 시작하는 일반·컬럼·폼 버튼 클릭
- 최신 데이터 수집 시작·완료·실패
- NAVER·Daum·Google Trends·Wikimedia의 출처별 시작과 실제 요청·성공·실패·생략·재시도 횟수
- YouTube 교환 파일 읽기 시작과 저장 결과
- 자동 저장 자료 정리의 시작·생략·삭제 결과
- 군집·통합 순위의 준비·계산·저장
- 주제 방향 대상 집계·Gemini 처리·저장
- 2차 군집 전체 스냅샷 집계
- 제목·사건·식별·기존 군집 관점별 Gemini 전송
- 2차 군집 관점 통합·결과 반영·작업 종료
- 2차 군집 완료 뒤 보류된 주제 방향 자동 생성 재개
- 모든 중앙 Gemini HTTP 전송의 시작·성공·실패

각 이벤트에는 시간, 실행 묶음, 종류, 상태, 작업명, 항목 수, 소요 시간, 실행 위치와 짧은 상세만 저장한다. 운영 로그 기록 실패는 실제 수집·군집·Gemini 작업을 취소하지 않는다.

프로그램 로그 화면은 다음을 지원한다.

- 조회 범위: 최근 100건·300건·500건
- 로그 종류: 전체·작업 중심·API만
- 표시 순서: 최신순·실행 흐름
- 같은 수집 실행 또는 2단계 군집 작업을 실행 ID로 묶어 그룹 안에서는 시작부터 종료까지 시간순 표시
- 시작·대기 행은 아직 결과가 없는 항목 수와 소요 시간을 `-`로 표시
- `실행 기록 종료` 같은 내부 명칭 대신 `최신 데이터 수집 실행 종료`처럼 실제 작업명 표시

`상태 새로고침`, `원격 브랜치 새로고침`처럼 조회만 다시 하는 버튼은 신규 프로그램 로그에 남기지 않는다. 실제 수집·정리·생성·업데이트 작업을 시작하는 버튼은 계속 기록한다.

## 로그 표시 형식

Streamlit에서 표시하는 운영 로그·Gemini 사용 로그·수집 이력·검색 요청 원장·군집 배치 로그에 같은 표시 규칙을 적용한다.

- 수량, 요청, 시도, 재시도, 처리 건수, 글자 수와 토큰 수는 천 단위 쉼표를 사용한다. 예: `1,234`, `1,234,567`.
- 밀리초로 저장된 소요 시간은 화면에서 초로 변환해 소수점 둘째 자리까지 표시한다. 예: `850ms`는 `0.85초`, `2분 3초`는 `123.00초`로 표시한다.
- 표의 소요 시간 열은 `시간(초)`, `소요 시간(초)`, `평균 소요(초)`처럼 단위를 열 이름에 표시한다.
- 날짜와 실제 발생 시각은 기존 `YYYY-MM-DD HH:MM:SS` 형식을 유지한다.
- 버전, 날짜·시각, 점수, 비율, 저장률, 순위와 `저장/요청` 같은 비율형 값은 수량 형식으로 바꾸지 않는다.
- 일반 데이터 표는 `시각·모델·기능·실행·오류·포털·검색어` 같은 로그 문맥과 수량·소요 열이 함께 있을 때만 공통 변환한다.
- Streamlit 함수가 다른 UI 래퍼로 다시 감싸져도 기존 공통 래퍼 표식을 내부 체인에서 찾아 중복 설치하지 않는다.
- DB에는 기존 밀리초 정수와 원본 집계값을 그대로 저장하며 화면 표시만 변환한다.

## 수집과 자동 정리 순서

화면 수동 수집과 Windows 예약 수집은 같은 순서를 사용한다.

```text
출처별 최신 자료 수집·저장
→ 자동 정리 실행 여부 확인과 오래된 미연결 자료 정리
→ 군집·통합 순위 계산
→ 필요하면 별도 2단계 군집 작업 시작
→ 2단계 군집 성공·남은 미처리 0 확인
→ 보류된 주제 방향 자동 생성 재개
```

수집 전에 하는 일은 자동 정리 활성화·마지막 실행일·보존기간을 읽는 준비뿐이며 실제 삭제는 출처 저장이 끝난 뒤 순위 계산 전에 실행한다. 수집이 예외로 중단되면 자동 정리를 실행하지 않는다. 자동 정리가 비활성화됐거나 오늘 이미 실행됐다면 수집 완료 뒤 `생략`으로 기록한다. 출처별 소요 시간은 전체 수집 시간이 아니라 각 출처의 실제 `timings` 값을 사용한다.

2단계 군집 작업이 `success`이고 `remaining_items = 0`일 때만 예약 수집과 동일한 주제 방향 생성 경로를 실행한다. 군집이 부분 완료·실패·중복 실행 생략 상태이거나 미처리가 남아 있으면 다음 수집으로 넘긴다. 후속 Gemini 실패는 이미 저장된 군집 성공을 취소하지 않는다.

## 2단계 군집 표시

한 작업은 미처리 자료의 고정 스냅샷을 한 번 준비한다. 따라서 과거 `완료 배치 1/20` 표시는 `처리 스냅샷 1/1`로 바꾼다.

군집 요약은 다음 값을 구분한다.

- 분석 관점 수: 제목·사건·식별·기존 군집 등 실제 사용한 관점 수
- 실제 Gemini 요청 수: 각 관점을 토큰 한도에 맞게 분할한 실제 HTTP 요청 수

상태 영역에는 현재 작업 회차, 현재 관점, Gemini 요청 번호, 해당 요청의 주제 수와 `호출 중·검증 중·통합 중·순위 계산 중` 단계를 한 문장으로 표시한다. 진행 막대 아래에는 최근 단계 로그를 시간순으로 표시한다.

- 실제 발생 시각: `YYYY-MM-DD HH:MM:SS`
- 작업 시작 이후 누적 경과: 초 단위 소수점 둘째 자리
- 단계 상태와 작업명
- 요청 주제 수, 예상 입력 토큰, 응답 검증 전환과 단계별 소요 시간

## 실행 경로

Streamlit 앱은 `src/__init__.py`에서 기록·수집 후 정리 계약을 설치한다. 별도 프로세스도 같은 계약을 사용하도록 다음 안전 실행기에 명시적으로 설치한다.

- `scripts/process_cluster_backlog.py`
- `scripts/refresh_trends_safe.py`
- `scripts/refresh_trends_dashboard.py`

`최신 데이터 수집·분석` 버튼과 `저장 자료 정리·순위 다시 계산` 버튼은 모두 별도 백그라운드 Python 프로세스를 시작한다. 앱 요청을 장시간 점유하지 않으며, 중복 실행은 기존 수집 잠금과 군집 작업 잠금이 거부한다. 화면 수동 수집은 `manual_refresh`, Windows 예약 수집은 `background_refresh`로 이력을 구분한다.

따라서 화면에서 실행한 수집·주제 방향 작업, Windows 예약 수집, 백그라운드 2단계 군집이 같은 프로그램 로그에 실행 단위로 남는다.
