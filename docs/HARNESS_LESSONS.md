# 개발 하네스 교훈

이 문서는 제품 로드맵이 아니라, ChatGPT나 Agent가 같은 실수를 반복하지 않고 적은 탐색으로 안전하게 수정·검증하기 위한 지속적인 하네스 교훈만 기록한다.

## 2026-08-08 개발 방향·하네스 점검

### 실제 런타임은 원본 함수 본문만으로 판단하지 않는다

개발 방향 점검에서 `scripts/refresh_trends.py`와 `app.py`의 표면적인 호출 순서만 보면 자동 정리가 출처 수집보다 먼저 실행되는 것처럼 보였다. 그러나 현재 Streamlit 실행 경로는 `src/__init__.py`가 `src/services/post_collection_cleanup_runtime.py`의 계약을 설치하며, 실제 의도는 다음 순서다.

```text
출처 수집·저장
→ 자동 정리
→ 군집·통합 순위 준비
```

`tests/test_post_collection_cleanup_runtime.py`와 `latest-data` 하네스가 이 계약을 검증한다. 따라서 Streamlit 호출 순서·로깅·웹 업데이트·군집 진행 같은 문제를 판단할 때는 직접 호출부뿐 아니라 `src/__init__.py`, 관련 `*_runtime.py` 설치 함수와 회귀 테스트를 함께 확인한 뒤 결론을 내린다.

### 탐색은 작업 범위부터 좁힌다

최신 `main`, 현재 작업 브랜치 관계와 `AGENTS.md`를 확인한 뒤 작업 종류에 맞는 코드·직접 호출부·설정·테스트·기준 문서만 읽는다. 긴 `README.md`, `AI_CONTEXT.md`, `NEXT_WORK.md`, 과거 릴리스와 Git 이력을 매 작업마다 전부 읽지 않는다.

### 검증은 관련 범위부터 넓힌다

개발 중에는 변경 영역에 대응하는 하네스 시나리오나 직접 관련 테스트를 먼저 실행한다. 실패 수정 후에는 영향받은 검증부터 다시 실행하고, 코드·운영 계약·하네스 수정이 안정된 뒤 `compileall`, 텍스트 검사, 전체 pytest를 최종 게이트로 사용한다. `all` 하네스를 작은 수정마다 반복하지 않는다.

### 하네스는 운영 환경의 대체물이 아니다

Agent 하네스는 임시 디렉터리, 임시 DB, 가짜 어댑터와 가짜 Gemini 응답으로 코드 계약을 확인한다. 실제 DB, `.env`, 외부 API, 브라우저 인증 상태, Windows 작업 스케줄러 등록 성공과 실제 콘텐츠 품질은 자동 하네스 통과로 간주하지 않는다.

### 제품이 넓어진 만큼 새 기능보다 완료 검증을 우선한다

현재 프로젝트는 수집부터 군집·글감·AI 요청·편집·사실 확인·발행 보조까지 주요 흐름이 이미 연결되어 있다. 앞으로 일반적인 "좋아 보이는 기능"을 추가하기보다 실제 사용에서 확인된 문제, 데이터 안전성, 실행 안정성, 핵심 흐름의 acceptance를 우선한다. 다만 이 문서는 `NEXT_WORK`를 대체하지 않으며, 실제 다음 작업은 최신 코드와 사용자 요청을 다시 확인해 결정한다.

## 2026-08-10 릴리스 적용 흐름 점검

### 적용 도구는 사용자가 시작 브랜치를 미리 맞추는 것을 전제로 하지 않는다

릴리스 후보가 정상이어도 사용자가 누적 `work/*` 브랜치에 있다는 이유만으로 최종 적용기가 즉시 실패하면 실제 사용자 흐름을 도구가 완결하지 못한 것이다. 릴리스 적용 진입점은 먼저 dirty/untracked 상태를 차단한 뒤, 깨끗한 `work/*`에서 `main` 전환을 안전하게 담당하고 최종 반영 엔진의 기존 검증을 그대로 사용한다. 실패 시 자동 stash·reset·clean으로 상태를 숨기지 않고, 가능하면 원래 작업 브랜치로 복귀한다.

이 계약은 `tests/test_apply_update_tool.py`와 `harness` 시나리오에서 회귀 검증한다. 최종 반영 엔진의 `behind 0, ahead 1`, 보호 파일 검사, 격리 검증, 반영 직전 원격 SHA 재확인과 일반 push 계약은 약화하지 않는다.

## 2026-08-12 하네스 라우팅 점검

### 시나리오 목록은 한 곳에서만 관리한다

`check_harness.ps1`과 Python 하네스가 같은 시나리오·별칭 목록을 각각 검증하면 새 시나리오를 한쪽에만 추가하는 실수가 생길 수 있다. 지원 시나리오, 별칭, 테스트 묶음은 `scripts/agent_test_harness.py`를 단일 기준으로 두고 BAT·PowerShell은 저장소 위치·Python 선택·인자 전달·종료 코드 처리만 담당한다.

### 반복되는 검증 경계만 시나리오로 승격한다

읽기 전용 운영 진단처럼 여러 테스트가 반복해서 함께 변경되고 직접 테스트 선택이 누락되기 쉬운 영역은 명시적 시나리오로 묶는 편이 탐색 비용과 검증 누락을 줄인다. 반대로 단일 테스트나 드문 보조 도구까지 시나리오로 만들면 하네스 자체가 새 유지보수 대상이 된다. 새 테스트가 기존 책임에 들어가면 기존 시나리오를 확장하고, 독립된 다중 테스트 경계가 실제로 생겼을 때만 새 시나리오를 추가한다.

## 유지 원칙

- 새 교훈이 반복 작업의 정확도·안전성·탐색 비용을 실제로 줄일 때만 추가한다.
- 일회성 버그 상세, 커밋 SHA, 테스트 개수처럼 금방 낡는 값은 적지 않는다.
- Git Hook, 복잡한 자동 테스트 선택기, 다중 Agent 오케스트레이션을 기본 해법으로 추가하지 않는다.
