# P2 읽기 전용 운영 진단

실제 `data\content_trend_tracker.duckdb`의 Gemini 주제 방향 표본, 주제 방향 대상 선정 흐름, NAVER·Daum 요청 원장, 출처 수집·Gemini 분리 상태와 최신 2단계 군집 작업을 읽기 전용으로 확인합니다. NAVER·Daum은 현재 사용자 개수 상한이 아니라 `trend_lookback_hours`의 최근 시간 범위 전체를 분석하므로, 별도 진단에서는 저장된 과거 상한 값과 실제 전체 범위 선택 결과가 분리되어 표시됩니다.

설정 화면의 `주제 방향 v6 품질·운영 진단`은 먼저 계산한 품질 진단 스냅샷을 아래 P2 통합 운영 판단에서도 그대로 재사용합니다. 같은 화면을 한 번 렌더링하면서 저장 계약·운영 표본을 다시 조회하지 않으며, CLI처럼 사전 계산값이 없는 호출만 품질 진단을 직접 집계합니다.

## 권장 실행

프로젝트 루트에서 다음 BAT를 실행합니다.

```powershell
.\run_operation_diagnostics.bat
```

최근 30일 포털 요청을 보려면 인자를 그대로 전달합니다.

```powershell
.\run_operation_diagnostics.bat --days 30
```

JSON 출력이 필요할 때만 다음과 같이 실행합니다.

```powershell
.\run_operation_diagnostics.bat --json
```

직접 실행도 가능합니다.

```powershell
.\.venv\Scripts\python.exe scripts\report_operation_diagnostics.py
```

NAVER·Daum의 최근 분석 범위 전체 적용 상태를 별도로 확인하려면 다음 BAT를 실행합니다.

```powershell
.\run_source_analysis_limit_diagnostics.bat
```

JSON이 필요하면 `--json`을 그대로 전달할 수 있습니다.

```powershell
.\run_source_analysis_limit_diagnostics.bat --json
```

이 보조 진단도 실제 DB를 `read_only=True`로 열고 실행 전후 DB·WAL 상태를 비교합니다.

## 주제 방향 대상 선정 흐름

현재 DB와 주제 방향 설정을 기준으로 다음 단계를 한 번에 표시합니다.

- 전체 군집
- 추천·검토 상태 군집
- 최소 기회 점수 통과 군집
- 기존 방향 완료 군집
- 생성 필요 군집
- 현재 요청 상한 안에서 확인한 군집
- 민감 제목 제외
- 근거 없음 제외
- 생성 대상 추정
- 요청 범위 밖 미검사

이 집계는 실제 주제 방향 생성을 호출하지 않습니다. 현재 요청 상한만큼 후보를 읽어 기존 생성 준비와 같은 민감 제목·근거 조건을 확인하고, `이번 확인 - 민감 제목 - 근거 없음`을 현재 생성 대상 추정으로 표시합니다. 따라서 실제 생성 시점에 DB나 설정이 달라지면 결과도 달라질 수 있습니다.

필수 테이블이나 컬럼이 없는 이전 DB, 또는 후보 근거를 읽을 수 없는 상태에서는 전체 진단을 중단하지 않고 `집계 불가`와 누락 테이블·오류 유형을 표시합니다. 이 진단 결과만으로 최소 점수, 요청 상한이나 Gemini 설정을 자동 변경하지 않습니다.

## Gemini 주제 방향 최종 실패 표본

주제 방향 v6 호출은 재시도 묶음별 마지막 완료 시도를 판정해 최근 최대 10건의 최종 실패를 표시합니다. 재시도 중 기록과 재시도 후 성공은 실패에서 제외합니다. 각 표본에는 현재 운영 조건 일치 여부, 상태, HTTP 코드, 오류 유형, 종료 사유, 당시 요청 수·설정 상한·사고 수준·제한 시간, 토큰과 소요 시간을 포함합니다. 원문 요청과 Gemini 응답 본문은 출력하지 않습니다.

최종 실패는 저장된 `error_type`, `finish_reason`, 오류 메시지를 조합해 다음 원인으로 분류합니다.

- `MAX_TOKENS·출력 한도`: 종료 사유가 `MAX_TOKENS` 계열이거나 출력 한도 메시지가 있는 경우
- `일일 할당량`: 일일 Gemini 할당량 소진
- `분당 제한·재시도 없음`: 분당 제한으로 종료됐지만 같은 요청 묶음에 저장된 재시도 기록이 없는 경우
- `재시도 후 분당 제한 종료`: 같은 요청 묶음에 실제 `retrying` 기록이 있고 이후에도 분당 제한으로 최종 종료된 경우
- `요청 제한 시간`: 설정된 요청 제한 시간 안에 응답이 완료되지 않은 경우
- `JSON 구문·절단`: JSON 파싱 오류, 잘린 문자열이나 불완전한 구조
- `cluster_id 검증`: 요청하지 않은 `cluster_id` 등 ID 검증 문제
- `기타 응답 검증`: 필수 항목, 방향 수, 근거 계약 등 나머지 응답 검증 문제
- `서비스·네트워크`, `요청·권한`, `기타`

현재 런타임에서 HTTP 200 응답의 일부 `cluster_id`만 유효하게 검증되면 이미 유효한 결과는 버리지 않고 그대로 보존하며, 누락·검증 탈락한 ID만 최대 한 번의 보강 요청으로 다시 보냅니다. 보강 요청은 원래 전체 묶음을 반복하지 않고 실제 누락 ID 수만 전송하며, Gemini 요청 원장에도 그 실제 요청 수량으로 별도 기록합니다. 보강으로 전체 요청 ID가 채워지면 실행 상태는 `success_after_retry`가 되고, 보강 후에도 일부가 남으면 기존 유효 결과를 저장한 채 남은 ID만 `response_partial`로 표시해 다음 실행 대상에 남깁니다. 최초 응답에서 유효 결과가 하나도 없는 전체 검증 실패는 이 부분 보강 경로로 다시 호출하지 않고 기존 실패 처리 계약을 유지합니다.

`MAX_TOKENS`와 JSON 오류가 함께 기록되면 출력 한도를 우선 원인으로 분류합니다. `invalid_api_response`라는 오류 유형만으로 JSON 구문 오류라고 판단하지 않으며, 실제 오류 메시지에 JSON 파싱 실패가 확인될 때만 `JSON 구문·절단`으로 분류합니다. HTTP 응답 JSON 자체는 읽혔지만 최상위 응답 객체 형태가 올바르지 않은 경우는 `기타 응답 검증`으로 분리합니다. 재시도 후 분당 제한으로 끝난 표본은 저장된 `retry_wait_seconds`를 합산해 실제 대기 시간을 함께 표시하고, JSON 출력에는 재시도 횟수·전체 대기·최대 단일 대기·재시도 원인을 포함합니다.

완료 시도가 아직 없는 `retrying` 기록만 존재하는 요청은 최종 실패로 단정하지 않습니다. 반대로 과거 DB에 재시도 행이 남아 있지 않으면 시도 번호가 2 이상이어도 실제 대기 시간은 0초로 표시될 수 있습니다. 이 경우 진단은 확인 가능한 기록만 사용하며 대기 시간을 추정하지 않습니다.

이 분류는 진단용이며 Gemini 설정이나 재시도 정책을 자동 변경하지 않습니다.

## NAVER·Daum 최근 분석 범위 전체 적용

`run_source_analysis_limit_diagnostics.bat`은 현재 `trend_lookback_hours`를 기준으로 실제 순위 준비 단계의 입력 선택 로직을 재사용해 다음 수량을 표시합니다.

- 현재 분석 모드 `portal_full_window`
- 조회 범위 안의 NAVER·Daum 최근 원문 수
- 실제 이번 분석에 선택되는 원문 수
- 선택 범위 밖에 남는 원문 수
- 최근 미군집 원문 수
- 선택된 미군집 원문과 범위 밖 미군집 원문 수
- 현재 선택 범위 안에서 2단계 군집 분석 대기로 남은 원문 수
- DB에 남아 있는 과거 호환 설정 `trend_analysis_naver_limit`·`trend_analysis_daum_limit`

현재 포털 분석은 사용자 개수 상한을 적용하지 않으므로 정상 상태에서는 `selected_items = recent_items`, `outside_limit_items = 0`, `outside_limit_unclustered_items = 0`입니다. 과거 `8,000` 같은 값은 `stored_legacy_limit`로 읽을 수 있지만 실제 선택 상한으로 사용하지 않습니다.

DuckDB partitioned TopN 엔진 보호를 위한 내부 SQL 안전 경계는 사용자 조정 상한과 별개이며, 이 진단 결과만으로 시간 범위나 군집 설정을 자동 변경하지 않습니다.

이 진단은 설정, 원문, 군집, 처리 상태를 수정하지 않으며 외부 API도 호출하지 않습니다. 필수 테이블이 없는 이전 DB에서는 누락 테이블 또는 오류 유형을 출력하고 임의로 마이그레이션하지 않습니다.

## 2단계 군집 안전 계약과 운영 지표

최신 `trend_clustering_jobs` 작업과 연결된 `trend_clustering_job_batches`를 함께 읽어 다음을 표시합니다.

- 외부 작업 스냅샷 설정 상한과 실제 완료 배치·최대 배치 번호
- 실제 최대 1차 단위 수, 스캔 설정 상한과 현재 절대 안전 상한
- 각 배치 시작·종료 시각의 완전성, 잘못된 시간 구간, 앞 배치 종료 전 다음 배치가 시작된 겹침 수
- 배치 간 최소·최대 간격과 순차 실행 계약 준수 여부
- 처리한 1차 군집·원문, 남은 원문
- 기존 2차 군집 연결·새 군집·불확실·충돌 차단·수동 검토 수
- 입력·출력·사고·전체 토큰과 처리 1차 군집 1,000개당 예상 전체 토큰
- 배치 평균·최대 처리 시간과 각 배치 상세

현재 `token_partitioned_snapshot` 계약은 한 작업에서 미처리 스냅샷을 최대 `50,000`개까지 한 번 준비하고 외부 작업 반복은 최대 1회로 제한합니다. `50,000`은 Gemini 요청당 후보 수가 아닙니다. 제목·사건·식별·기존 군집 관점은 목표 입력 토큰과 TPM에 맞춰 필요한 수만큼 나뉘며 Gemini 요청은 한 번에 하나씩 순차 실행됩니다.

과거 고정 후보 수 방식의 작업 이력은 기존 의미로 계속 읽을 수 있지만, 사람용 현재 계약 표시에서는 과거 `300개` 절대 상한이나 `20회` 반복을 현행 기준으로 표시하지 않습니다.

1차 군집은 `must_merge`, `must_split`, `undetermined` 규칙을 사용합니다. 같은 URL·안전한 동일 제목이라도 날짜·회차·제품·행동·방향이 충돌하면 분리하고, 동일 회차·동일 제품과 행동처럼 강한 공통 근거가 있을 때만 추가 병합합니다. 확실하지 않은 후보는 억지로 병합하지 않습니다.

2차 군집은 실제 `trend_*` ID를 Gemini에 노출하지 않습니다. 후보마다 1부터 다시 시작하는 로컬 `option_id`만 전달하고, 응답을 받은 뒤 프로그램이 해당 후보의 실제 기존 군집 ID로 변환합니다. 범위를 벗어난 번호, 규칙 충돌, 낮은 신뢰도와 누락 응답은 자동 연결하지 않고 불확실·검토 대상으로 유지합니다.

순차 실행 계약은 모든 완료 배치에 시작·종료 시각이 있고, 각 배치의 종료가 시작보다 빠르지 않으며, 다음 배치가 앞 배치 종료 전 시작하지 않았을 때 통과합니다. 배치 간 고정 대기시간을 요구하지 않으므로 간격이 `0.0초`여도 앞 요청과 저장이 끝난 뒤 다음 요청이 시작됐다면 정상입니다.

### 2단계 rate limit·cooldown 원인 분류

P2 운영 진단은 `trend_clustering_request_metrics`의 최근 요청을 읽어 로컬 속도조절과 Gemini 공급자 제한을 분리합니다.

- `tpm_wait_seconds > 0`: Gemini 호출 전에 프로그램의 로컬 TPM 리미터가 기다린 시간입니다. 공급자가 요청을 거절한 것이 아니므로 정상적인 사전 속도조절로 봅니다.
- `error_type=rate_limited`: Gemini가 실제로 일시적인 rate limit을 반환한 요청입니다.
- `error_type=daily_quota_exhausted`: 일일 quota가 소진된 공급자 제한입니다.
- 그 밖의 오류는 `기타 오류`로 집계하되 rate limit으로 바꾸어 해석하지 않습니다.

사람용 출력은 최근 요청 수, 로컬 TPM 대기 횟수·합계·최대 시간, 공급자 rate limit·일일 quota·기타 오류 횟수를 함께 표시합니다. `local_tpm_wait_only`는 오류가 아니라 자체 속도조절 상태입니다. 공급자 제한과 로컬 TPM 대기가 같은 표본에 함께 있으면 공급자 제한을 우선 분류합니다.

이 요청 메트릭에는 `job_id`가 없으므로 최근 요청 표본을 최신 군집 작업의 직접 원인이라고 단정하지 않습니다. 최신 군집 작업 자체가 `failed`인 경우에만 최근 표본의 `rate_limited` 또는 `daily_quota_exhausted` 신호를 다음 점검 사유로 보조 사용하며, 성공·진행 중인 최신 작업은 과거 제한 기록 때문에 실패로 재분류하지 않습니다.

이 진단은 읽기 전용이며 TPM 상한, cooldown, Gemini 재시도 정책을 자동 변경하지 않습니다.

### 군집 품질 표본

최신 작업에 실제 군집 표본이 있으면 `trend_clustering.quality_sample`에서 저장 결과를 다시 계산하지 않고 읽기 전용으로 재구성합니다.

- `first_stage_key`를 기준으로 그 작업에서 처리한 1차 후보를 복원합니다.
- 현재 군집에 작업 이전 원문이 함께 있으면 `기존 연결`, 작업 후보가 2개 이상 함께 있으면 `다중 신규`, 작업 후보 1개만 있으면 `단독 신규` 표본으로 분류합니다.
- `retry`와 `needs_review`는 미확정 표본으로 별도 표시합니다.
- 작업의 `processed_units`, `existing_links`, `new_clusters`, `uncertain_units`, `needs_review_items`와 재구성 수치가 모두 일치하는지 확인합니다.
- 현재 `trend_clusters.calculated_at` 스냅샷이 해당 작업 시각 범위와 일치하지 않으면 이후 계산이 결과를 교체한 것으로 보고 `reconstruction_reliable=false`로 표시합니다.
- 스냅샷과 작업 집계가 모두 맞고 후보 식별이 완전할 때만 `reconstruction_reliable=true`입니다.
- 최대 8개 대표 제목 표본을 보여 주지만 단독 후보 비율만으로 과분리나 병합 임계값 문제를 자동 판정하지 않습니다.

테이블이나 필수 컬럼이 없는 이전 DB는 진단을 실패시키지 않고 `집계 불가`와 누락 항목을 표시합니다. 결과는 설정 확대나 군집 자동 병합을 수행하지 않으며, 불확실·충돌·검토 대상은 실제 표본을 확인하기 위한 신호로만 사용합니다.

## 무변경 검증

진단은 DuckDB를 `read_only=True`로 연결합니다. 연결 전후에 다음 상태를 추가로 비교합니다.

- DB 파일 존재 여부
- DB 파일 크기
- DB 파일 수정 시각
- `.wal` 파일 존재 여부
- `.wal` 파일 크기와 수정 시각

모두 같으면 `DB 무변경 검증: 통과`를 표시합니다. 진단 도중 자동 수집이나 앱이 DB를 변경해 전후 상태가 달라지면 무변경을 증명할 수 없으므로 종료 코드 `3`으로 중단합니다. 이 경우 앱과 자동 수집이 쓰기 작업을 하지 않는 시점에 다시 실행합니다.

## 종료 코드

- `0`: 진단과 DB 무변경 검증 성공
- `1`: DuckDB 연결 또는 진단 집계 실패
- `2`: 지정한 DB 파일 없음
- `3`: 진단 전후 DB 또는 WAL 상태 변경

## 판단 원칙

- 현재 런타임 조건과 일치한 성공 요청만 표본에 포함합니다.
- 실패 요청과 다른 처리량·사고 수준·제한 시간의 요청을 현재 성공 표본에 섞지 않습니다.
- 표본 부족과 실제 오류를 구분합니다.
- 주제 방향 대상 선정은 현재 요청 상한 안의 읽기 전용 추정이며 실제 생성 결과로 단정하지 않습니다.
- 최종 실패 분류는 저장된 종료 사유, 오류 정보와 재시도 원장에 근거하며 기록되지 않은 대기 시간을 추정하지 않습니다.
- NAVER·Daum은 현재 시간 범위 전체 분석과 저장된 과거 호환 상한 값을 구분합니다.
- 2단계 제한 원인은 로컬 `tpm_wait_seconds`와 공급자 `rate_limited`·`daily_quota_exhausted`를 분리하고 최근 요청을 특정 job의 직접 원인으로 추정하지 않습니다.
- 군집 품질 표본은 `reconstruction_reliable=true`인지 먼저 확인하고, 단독 후보 수치와 실제 제목 사례를 함께 봅니다.
- 진단 결과만으로 Gemini 처리량, 사고 수준, 프롬프트, 군집 기준이나 분석 시간 범위를 자동 변경하지 않습니다.
- `.env`, API 키, DB, WAL과 로그를 외부에 전달하지 않습니다.
