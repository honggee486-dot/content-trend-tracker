# 트렌드 군집 처리 운영 계약

## 목적

군집 결과의 오병합을 줄이면서도 전체 미처리 후보를 제목·사건·식별 정보·기존 군집 관점에서 검토한다. 요청 후보 수를 고정하지 않고 실제 입력 토큰과 Gemini 입력 TPM을 기준으로 처리량을 조절한다.

## 1차 군집

1차 자동 병합은 확실한 경우만 허용한다.

- 동일 외부 ID·안전한 동일 URL
- 강한 식별 정보 충돌이 없는 완전 동일 정규화 제목
- 날짜·회차·제품·행동·방향 충돌이 있으면 강제 분리
- 제목이 비슷하거나 같은 기업·인물·제품군이라는 이유만으로 자동 병합하지 않음
- 기존 군집 후보 탐색에서는 `특징`, `선택`, `포인트`, `총정리`와 조사 결합형 표현을 사건·제품 식별 근거에서 제외하며, 이런 편집 템플릿만 공통인 서로 다른 상품은 기존 군집 후보로 올리지 않음

1차에서 덜 묶인 후보는 2차 판단 대상으로 남긴다.

## 2차 군집

작업 시작 시 미처리 전체 스냅샷을 한 번만 고정한다. 기존의 `외부 최대 20라운드 × 관점별 호출` 중첩 반복은 사용하지 않는다. 고정한 스냅샷을 관점별로 주제순 정렬하고 다음 순서로 검토한다.

1. 제목 표현
2. 주체·대상·제품·행동으로 구성한 사건 의미
3. 날짜·회차·제품 세대·행동·상승·하락 등 식별·충돌 정보
4. 기존 군집 후보와의 연결

각 관점은 입력 토큰 목표에 맞춰 필요한 수만큼 나뉜다. Gemini 요청 동시 실행 수는 `1`이며 다음 순서를 지킨다.

```text
현재 요청 전송
→ 응답 수신
→ 종료 사유·JSON·후보 번호 검증
→ 토큰 실측·TPM 기록
→ 필요한 대기
→ 다음 요청 전송
```

따라서 같은 작업에서 여러 관점이나 토큰 조각을 동시에 전송하지 않는다. 화면에 같은 저장 시각으로 보이는 호출이 있더라도 요청 실행은 위 순서로 직렬 처리하며, 상세 소요 시간과 TPM 대기는 군집 전용 로그에서 확인한다.

각 요청은 긴 내부 ID 대신 요청 안에서만 유효한 짧은 후보 번호를 사용한다. Gemini는 다음 내용만 희소 응답으로 반환한다.

- 기존 군집에 연결할 후보
- 두 개 이상으로 구성된 신규 그룹
- 명시적으로 불확실한 후보
- 병합을 막아야 하는 후보 간 충돌

`existing_links`, `new_groups`, `uncertain_nos`는 후보 기준으로 서로 배타적이다. 한 응답에서 같은 `candidate_no`를 이 세 범주에 두 번 이상 넣거나 하나의 신규 그룹 안에서 같은 번호를 반복하면 프로그램은 그 후보를 자동 채택하지 않고 중복 응답으로 검증 탈락시켜 불확실 대상으로 유지한다. `conflicts`는 병합 차단 근거라 같은 후보를 참조할 수 있다.

신규 그룹은 입력 제목 문자열을 다시 출력하지 않는다. Gemini는 `candidate_nos` 안에서 가장 대표적인 원본 제목의 번호 하나를 `representative_candidate_no`로 선택하고, 프로그램이 그 번호의 원래 제목을 내부 `representative_title`로 복원한다. 선택 번호가 그룹 구성원에 없거나 원본 제목을 확인할 수 없으면 해당 그룹을 검증 탈락시킨다. 따라서 Gemini가 대표 후보를 고르는 판단은 유지하면서 입력 `title`·`examples`·`existing_options` 문자열의 반복 출력만 제거하고, 이후 저장·표시 계층이 사용하는 대표 제목 필드와 품질 계약은 유지한다.

한 관점에서 반환되지 않은 후보는 즉시 확정하지 않는다. 모든 필수 관점이 정상 완료된 뒤에도 관계·불확실성이 발견되지 않은 후보만 단독 군집으로 확정한다. 신규 병합과 기존 군집 연결은 기본적으로 서로 다른 두 관점의 동의와 안전 규칙 통과가 필요하다.

## 입력 토큰과 TPM

- Gemini 입력 TPM: `250,000`
- 자동 배치 목표: `225,000` 입력 토큰, TPM의 90%
- 절대 안전 경계: `245,000` 입력 토큰
- 최근 60초 입력 토큰 합계가 250,000을 넘으면 다음 요청을 대기
- 요청 전에 예상 입력 토큰을 예약하고 응답 후 실제 입력 토큰으로 보정
- 실패·시간 초과처럼 실제 사용량이 불명확한 요청은 예상량을 60초 동안 사용한 것으로 유지

후보 개수는 요청 상한이 아니다. 제목만 보내는 관점은 더 많은 후보가 들어가고, 사건 정보와 기존 군집 예시가 포함되는 관점은 더 적게 들어간다.

주제 경계를 우선 보존한다. 한 주제 묶음이 225,000토큰을 넘는 경우에만 여러 요청으로 나누고, 경계 후보를 소량 겹쳐 배치 간 누락 가능성을 낮춘다.

## 보수적 자동 보정

입력 토큰 추정은 실제보다 약간 높게 시작한다.

- 최근 3회가 연속으로 정상이고 여유가 확인된 경우에만 배치 용량을 약 2% 확대
- 실제 입력이 예상보다 크거나 목표 225,000을 넘으면 즉시 보수적으로 축소
- Rate limit·TPM 오류가 발생하면 일반 초과보다 더 크게 축소
- 자동 확대는 목표 225,000토큰을 넘지 않음
- 최근 호출의 요청 문자 수와 실제 입력 토큰 비율을 다음 실행의 초기 추정에 반영

## 수집·군집 잠금 소유자와 lease

수집 잠금과 군집 잠금은 PID뿐 아니라 프로세스 시작 식별자와 갱신 가능한 lease를 함께 저장한다.

- Windows에서는 `GetProcessTimes`의 생성 시각 FILETIME을 사용한다.
- Linux에서는 `/proc/<pid>/stat`의 시작 tick을 사용한다.
- PID가 살아 있어도 시작 식별자가 다르면 Windows PID 재사용으로 판단해 오래된 잠금을 교체할 수 있다.
- 새 잠금은 `heartbeat_at`과 `lease_seconds`를 기록하며 기본 heartbeat 간격은 30초, lease는 180초다.
- 잠금 소유 프로세스의 daemon heartbeat 스레드는 DB 연결 없이 잠금 메타데이터만 원자적으로 갱신한다.
- PID와 시작 식별자가 같더라도 heartbeat가 lease를 초과해 오래되면 중단된 작업으로 판정할 수 있다.
- 기존 잠금처럼 시작 식별자나 lease가 없으면 PID 생존 확인만 사용하는 하위 호환 경로를 유지한다.
- 잘못된 heartbeat 값이나 권한·플랫폼 제약으로 프로세스 시작 식별자를 읽지 못하면 실행 중인 작업을 잘못 삭제하지 않도록 보수적으로 활성 상태로 판단한다.
- 갱신과 잠금 해제는 token이 일치하는 소유자만 수행하며, 다른 작업이 잠금을 교체한 뒤에는 이전 heartbeat가 새 잠금을 갱신하지 않는다.

`trend_clustering_jobs`의 오래된 `queued`·`running` 행은 DB heartbeat가 오래됐다는 이유만으로 `failed`로 자동 변경하지 않는다. DB heartbeat freshness는 새 작업의 중복 생성 여부를 빠르게 판단하는 내부 기준일 뿐, 화면에서 작업 중단을 확정하는 근거로 사용하지 않는다. heartbeat가 없는 구형 행은 화면 판단에 `created_at`을 대신 사용한다.

Streamlit 화면의 최종 상태 판정은 수집·군집 잠금을 읽기 전용으로 확인한 뒤 적용한다. 저장된 `queued`·`running` 이력이 마지막 DB 진행 갱신 후 6시간 이상 지났고, 수집 잠금과 군집 잠금의 PID 시작 식별자·heartbeat/lease를 모두 확인한 결과 현재 활성 작업을 뒷받침하지 않을 때만 `상태 확인 필요`로 표시한다. 잠금 중 하나라도 현재 활성 상태이거나 잠금 상태를 신뢰성 있게 읽지 못한 경우에는 시간만으로 중단을 추정하지 않고 기존 `대기`·`실행 중` 표시를 유지한다. 이 판정은 DB 행을 수정하지 않는다.

최근 실행 시도가 오래된 `queued`·`running` 이력이라면, DB freshness 기준에서 현재 활성 작업으로 분류되지 않더라도 대표 카드에서 과거 성공 결과로 숨기지 않고 위 잠금 근거 기반 상태를 보여준다. `skipped_overlap` 시도만 있는 경우를 실제 처리 결과처럼 대표 카드에 올리지 않는 기존 규칙은 유지한다.

오래된 DB 이력을 제외하고 새 작업을 대기열에 넣더라도 실제 군집 실행은 반드시 `trend_clustering.lock`을 획득한 뒤 시작한다. 기존 프로세스가 PID 시작 식별자와 유효한 lease를 가진 실제 잠금 소유자로 확인되면 새 작업은 실행하지 않고 그 새 시도만 `skipped_overlap`으로 종료한다. 반대로 잠금이 실제로 만료됐거나 소유자가 사라진 경우에만 잠금 계층이 교체를 허용한다. 작업을 소유한 프로세스가 정상 완료하거나 명시적으로 실패한 경우에는 그 작업 자신의 최종 상태를 기존과 같이 저장한다.

오래된 `running` 이력을 자동 복구하는 별도 정책은 현재 계약에 포함하지 않는다. 실제 행을 완료·실패로 수정하려면 잠금·프로세스 근거, 사용자 확인과 기존 기록 보존 정책을 별도로 설계한 뒤 적용한다.

최신 데이터 수집의 짧은 연결 경로가 같은 프로세스 안에서 직접 2단계 군집을 수행한 경우에도 완료 결과를 `trend_clustering_jobs`와 `trend_clustering_job_batches`에 남긴다. 이 이력은 `launcher=trend-refresh-ranking`으로 구분하며 이미 수행한 군집을 기록할 뿐 추가 Gemini 호출을 만들지 않는다. 군집 계산 중에는 기존처럼 DuckDB 연결을 닫고, 결과 저장 연결에서 기존 군집 결과를 확정한 직후 같은 군집 잠금이 유지되는 동안 원장을 기록한다. 따라서 `trend_cluster_processing`이 갱신됐는데 대응 최신 job이 없어 P2 품질 진단이 과거 작업을 참조하는 상태를 새 실행부터 만들지 않는다. 과거 DB의 누락 원장은 추정으로 역작성하지 않는다.

## 로그

기존 `gemini_api_calls`에는 요청·응답 토큰, 종료 사유와 결과를 남긴다. 군집 전용 세부 지표는 `trend_clustering_request_metrics`에 추가 저장한다.

- 분석 관점
- 요청 후보 수와 요청 문자 수
- 예상·실제 입력 토큰
- 목표·절대 경계·TPM 한도
- 직전 60초 사용량과 전송 전 대기시간
- 추정 계수
- API 소요 시간
- `finish_reason`
- 상태와 오류 유형

실제 운영 로그를 모은 뒤 토큰 목표와 전송 속도를 조정하며, 초기 구현에서는 속도보다 Rate limit 회피와 오병합 방지를 우선한다.
