# P3 NAVER·Daum 최근 분석 범위 전체 적용

## 결정

P2 실제 운영 진단에서 NAVER·Daum 원문이 최근 72시간 안에 충분히 수집되어 있어도 기존 출처별 개수 상한 뒤의 미군집 원문이 순위·군집 입력에서 제외되는 현상을 확인했다.

P3에서는 다른 Gemini·군집 품질 축을 함께 바꾸지 않고 **NAVER·Daum 사용자 분석 입력 개수 상한만 제거**한다.

- `trend_lookback_hours`가 실제 분석 시간 범위다. 기본값은 최근 72시간이다.
- NAVER 뉴스·블로그는 이 시간 범위 안의 원문 전체를 순위·군집 준비 입력으로 읽는다.
- Daum 웹문서·카페도 같은 방식으로 시간 범위 안의 원문 전체를 읽는다.
- YouTube·Google Trends·위키백과의 기존 출처별 분석량 제한은 유지한다.
- 이 변경은 수집 API 호출량을 늘리는 설정이 아니다. 이미 DuckDB에 저장된 원문을 순위·군집 준비 단계에서 얼마나 읽는지에만 영향을 준다.
- 2단계 Gemini 군집의 토큰 분할·순차 실행·잠금·처리 상한 계약은 별도이며 이번 P3에서 바꾸지 않는다.
- DuckDB partitioned TopN의 엔진 조건을 넘지 않도록 내부 SQL 방어 경계는 포털 그룹당 `999,999`개로 둔다. 이는 사용자 조정 상한이 아니며 현재 72시간 운영 규모보다 충분히 큰 비상 안전장치다.

## 기존 설정 호환

기존 DB에는 `trend_analysis_naver_limit`, `trend_analysis_daum_limit`에 `4,000`, `8,000` 등 과거 UI 상한 값이 남아 있을 수 있다.

- 기존 값을 삭제하거나 DB 행을 강제로 마이그레이션하지 않는다.
- 런타임은 과거 UI 범위였던 500 이상 값을 **최근 분석 시간 범위 전체** 의미로 해석한다.
- 새 기본값과 설정 화면 저장값은 `0`을 사용하며 `0 = 최근 분석 시간 범위 전체`다.
- 설정 화면에서는 NAVER·Daum 숫자 상한 대신 `최근 분석 범위 전체`를 읽기 전용으로 표시한다.
- 테스트·내부 진단에서만 10~499의 작은 명시적 제한값을 사용할 수 있어 기존 bounded fixture를 유지한다.

## 진단 계약

기존 `run_source_analysis_limit_diagnostics.bat` 파일명은 호환을 위해 유지하지만 출력 의미는 전체 범위 적용 확인으로 바뀐다.

정상적인 운영 규모에서는 각 포털에 대해 다음이 성립해야 한다.

- `analysis_mode = full_window`
- `configured_limit = 0`
- `selected_items = recent_items`
- `outside_limit_items = 0`
- `outside_limit_unclustered_items = 0`

`stored_legacy_limit`은 기존 DB에 남아 있는 과거 상한 값이며 현재 분석에는 적용하지 않는다. 최근 분석 시간 범위 안의 단일 포털 그룹이 내부 SQL 방어 경계 `999,999`개를 초과하는 비정상 규모에서는 전체 범위 계약을 보호하기보다 엔진 안전을 우선하고 진단의 범위 밖 수량으로 드러낸다.

진단은 계속 `read_only=True`로 DB를 열고 실행 전후 DB·WAL 상태를 비교한다. 외부 API, Gemini, 실제 군집 저장은 호출하지 않는다.

## 성능·안전 판단

전체 범위 적용은 API 호출량이나 Gemini 요청 개수를 직접 늘리는 옵션이 아니지만, 로컬 순위 준비 단계가 읽고 정규화하는 원문 수는 늘 수 있다. 따라서 실제 운영에서는 다음을 관찰한다.

1. 최신 데이터 수집·순위 재계산의 로컬 계산 시간
2. DuckDB 연결 유지 시간이 과도하게 늘지 않는지
3. 미처리 원문이 사용자 개수 상한 때문에 다시 제외되지 않는지
4. 2단계 군집의 기존 토큰·순차 실행 계약이 그대로 유지되는지

성능 문제가 실제 표본에서 확인되기 전에는 시간 범위를 줄이거나 다른 군집·Gemini 설정을 동시에 변경하지 않는다.
