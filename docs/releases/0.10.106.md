# 0.10.106 운영 진단 신뢰성과 군집 품질 안정화

## 핵심 변경

### NAVER·Daum 최근 범위 전체 분석

- NAVER·Daum 분석 대상을 사용자 개수 상한으로 자르지 않고 `trend_lookback_hours` 최근 시간 범위 전체에서 선택합니다.
- 기존 DB의 포털 분석 상한 설정값은 삭제하지 않고 하위 호환 입력으로 보존하되 현재 분석 범위를 제한하는 값으로 사용하지 않습니다.
- DuckDB partitioned TopN 엔진을 보호하기 위한 그룹당 `999,999`개 내부 SQL 방어 경계만 유지하며 사용자 조정 상한으로 노출하지 않습니다.
- 읽기 전용 출처 진단에서 최근 항목과 실제 선택 항목, 상한 밖 미처리 항목을 구분해 전체 범위 계약이 실제 저장 상태와 맞는지 확인할 수 있습니다.

### P2 읽기 전용 운영 진단

- `run_p2_diagnostics.bat`과 관련 진단 서비스·CLI를 추가해 실제 DuckDB를 수정하지 않고 수집·Gemini·군집 상태를 한 번에 점검할 수 있습니다.
- 같은 스냅샷을 재사용해 여러 진단이 불필요하게 DB를 다시 열지 않도록 하고, 실제 DB 파일과 WAL을 변경하지 않는 읽기 전용 계약을 테스트합니다.
- Gemini 현재 조건과 과거 조건을 구분해 요청량·사고 수준·제한 시간·종료 사유·재시도·검증 실패를 해석합니다.
- 수집 출처 성공과 Gemini 후처리 실패를 분리해 한 출처나 후처리 실패가 정상 수집 결과를 취소하지 않는 기존 부분 성공 원칙을 유지합니다.

### 2단계 군집 진단 계약 정합화

- 현재 군집 런타임의 `50,000`은 Gemini 요청당 후보 수가 아니라 한 작업의 내부 스냅샷 스캔 안전 상한으로 해석합니다.
- 외부 군집 작업은 한 번의 스냅샷을 고정하고 제목·사건·식별·기존 군집 관점을 입력 토큰과 TPM에 맞춰 순차 분할합니다.
- 과거 `고정 후보 수 × 최대 배치` 방식으로 저장된 작업 이력은 기존 의미로 계속 읽을 수 있도록 호환성을 유지합니다.
- 진단 화면과 운영 문서가 현재 토큰 분할 런타임을 과거 계약으로 오판하지 않도록 맞췄습니다.

### 저장된 군집 품질 표본

- 최신 군집 작업의 `first_stage_key`와 저장 군집·원문을 연결해 다중 신규, 기존 군집 연결, 단독 신규, `retry`, `needs_review`의 실제 제목 표본을 읽기 전용으로 재구성합니다.
- 작업 원장 수치와 현재 군집 스냅샷 시각·집계가 일치할 때만 `reconstruction_reliable=true`로 표시합니다.
- 후속 군집으로 스냅샷이 바뀌었으면 현재 상태를 과거 작업 결과라고 추정하지 않고 신뢰 불가 사유를 명시합니다.
- 단독 후보 비율 같은 집계 하나만으로 과분리·오병합을 자동 판정하지 않고 실제 제목 표본을 함께 보도록 제한합니다.

### 일반 편집 템플릿 기반 기존 군집 오병합 방어

- 실제 품질 표본에서 서로 다른 상품인 원형파라솔과 IP2726 모니터가 `특징`, `선택`, `포인트`, `총정리` 같은 일반 편집 표현을 공유해 기존 군집 후보 경로에서 만날 수 있던 원인을 확인했습니다.
- 기존 군집 후보 인덱스는 이런 일반 템플릿 단어와 조사 결합형 표현을 식별 토큰으로 사용하지 않습니다.
- 실제 상품명·모델명·사건 식별 토큰을 공유하는 후보는 기존처럼 연결 후보가 될 수 있어 정상 동일 상품 연결을 유지합니다.
- 이 변경은 전역 군집 임계값이나 Gemini 프롬프트·모델·TPM 설정을 함께 조정하지 않는 단일 축 품질 수정입니다.

### 수집 이력과 오래된 실행 표시

- 수집 이력 화면의 상태·실행 종류·Gemini 결과 필터를 화면 전용 서비스로 분리했습니다.
- 오래된 `running` 기록은 DB 행을 바꾸지 않고 수집·군집 잠금 상태가 현재 작업을 뒷받침하지 않을 때만 `상태 확인 필요`로 표시합니다.
- 잠금 상태를 신뢰성 있게 읽지 못하면 시간만으로 실패를 추정하지 않습니다.

### 개발 하네스와 자동 회귀검증

- `AGENTS.md`에 작업 종류별 확인 경로와 변경 영역별 검증 라우팅을 정리했습니다.
- 실제 DB·외부 API·Windows 작업 스케줄러를 사용하지 않는 선택형 Agent 하네스를 정비하고 군집 품질·진단 회귀 테스트를 연결했습니다.
- GitHub Actions에 Windows Python CI와 격리 Chromium Browser Regression을 추가해 구문·텍스트 위생·전체 pytest와 제작 흐름 브라우저 계약을 자동 확인합니다.
- 최종 릴리스 적용은 `scripts/apply_update_release.ps1`을 통해 `main` 또는 깨끗한 `work/*` 브랜치에서 시작할 수 있습니다. `work/*`에서 시작하면 안전하게 `main`으로 전환한 뒤 기존 최종 반영 엔진을 실행하고, 실패 시 작업 트리가 깨끗하면 원래 작업 브랜치로 복귀합니다.

## 데이터 호환성과 안전

- 기존 DuckDB 테이블·컬럼·상태 의미를 삭제하거나 변경하지 않습니다.
- 실제 진단 경로는 읽기 전용이며 기존 원본, 군집, 주제, 자료팩, AI 응답, 초안, 리비전, 사실 확인과 발행 기록을 자동 수정하지 않습니다.
- `.env`, API 키, 실제 DB·WAL·잠금, Parquet, 로그와 브라우저 인증 상태를 저장소에 포함하지 않습니다.
- 외부 API 대기 중 DuckDB 연결을 장시간 유지하지 않고 출처별 부분 성공 원칙을 유지합니다.
- 자동 로그인, 쿠키 저장, CAPTCHA 우회와 무인 자동 게시를 추가하지 않습니다.

## 적용 후 확인

1. `run_p2_diagnostics.bat`의 읽기 전용 진단이 실제 DB를 변경하지 않고 현재 수집·Gemini·군집 상태를 설명하는지 확인합니다.
2. 다음 정상 수집·군집 후 `quality_sample`이 최신 작업과 스냅샷이 일치할 때만 신뢰 가능으로 표시되는지 확인합니다.
3. 기존 군집 연결에서 일반 편집 템플릿만 공유하는 서로 다른 상품이 다시 후보로 노출되지 않는지 실제 제목 표본을 확인합니다.
4. 과분리·병합 누락은 단독 후보 비율만으로 판단하지 않고 다중 신규·기존 연결·미확정 제목을 함께 비교합니다.
5. `run_app.bat`, `Ctrl+C`, `stop_app.bat`, 웹 업데이트 뒤 재시작과 8518 단일 인스턴스 계약을 실제 Windows 환경에서 확인합니다.
6. 실제 사용자 데이터에서 작업 대기열 → AI 요청서 → AI 결과 → 편집 → 발행 보조 흐름을 한 번 확인합니다.

## 검증 상태

릴리스 후보는 최신 `origin/main`을 직접 부모로 하는 단일 커밋으로 구성하고 `behind 0, ahead 1` 관계를 만족해야 합니다. GitHub CI의 Python 구문 검사·텍스트 위생·전체 pytest와 격리 Chromium Browser Regression이 모두 통과한 후보만 실제 `main` 반영 대상으로 사용합니다.

실제 DuckDB 쓰기, 외부 Gemini·NAVER·Daum 호출, Windows 프로세스 생명주기와 브라우저 인증 상태는 자동 릴리스 검증에 포함하지 않으며 위 적용 후 확인 항목으로 분리합니다.
