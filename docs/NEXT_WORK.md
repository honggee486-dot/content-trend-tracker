# 다음 작업

## 0.10.109 릴리스 범위

`0.10.109`는 `0.10.108`의 수집 후 정리 안전 경계를 유지하면서 대시보드 진행 표시, deterministic baseline 읽기 전용 진단 신뢰성, 운영·P2 진단 연결과 개발 하네스 라우팅을 실제 현재 코드에 맞추는 안정화 릴리스다. 생산 군집 규칙·DB 스키마·외부 API·인증·의존성 계약은 변경하지 않는다.

- 대시보드의 자동 정리 초반 단계는 조건 확인·예약임을 명확히 하고 실제 정리 결과는 출처 저장 뒤 순위 준비 직전 실행 결과로 표시한다.
- 전체 출처 실패는 예약 정리 보류와 기존 순위·보존 자료 유지를 표시하고, `skipped_overlap`은 기존 군집 작업으로 순위 재계산이 보류됐음을 완료와 구분한다.
- deterministic baseline은 재구성·비교가 완전한 표본에서만 일치·불일치 집계를 판단 근거로 노출하고, 사람용 진단에는 현재 군집과 baseline의 대표 제목 비교 표본을 제공한다.
- 운영·P2 진단은 동일한 군집 품질 runtime 결과를 재사용해 품질 표본과 baseline을 중복 계산하지 않는다.
- 개발 하네스는 Python 시나리오 매핑을 단일 기준으로 사용하고, `diagnostics` 시나리오는 운영 진단·NAVER/Daum 전체 범위·P2 통합 진입점을 함께 검증한다.
- 릴리스 후보는 최신 `origin/main` 직접 자식의 단일 커밋, `behind 0 / ahead 1` 관계를 유지한다.
- `VERSION`, `CHANGELOG.md`, `AI_CONTEXT.md`, 이 문서, `docs/releases/0.10.109.md`와 릴리스 정합성 테스트를 `0.10.109` 기준으로 맞춘다.
- 실제 DB·외부 API·Windows 작업 스케줄러·실사용 로그인 브라우저는 릴리스 자동 검증에 사용하지 않는다.

### 0.10.109 적용 후 실사용 확인

1. 정상 수집에서 진행 이력이 `정리 조건 확인/예약 → 출처 수집·저장 → 실제 정리 결과 → 순위·군집 → 주제 방향` 순서로 보이는지 확인한다.
2. 전체 출처 실패와 `skipped_overlap` 상황에서 기존 데이터 보존·순위 보류 상태가 완료 문구와 혼동되지 않는지 확인한다.
3. `run_p2_diagnostics.bat`의 deterministic baseline 사람용 표본에서 현재 군집·baseline 대표 제목과 비교 완전성 상태를 확인한다.
4. baseline 품질이 동일하거나 개선되면서 Gemini 호출·토큰·처리 시간이 실제로 줄어드는 근거가 생길 때만 ambiguous-only Gemini 생산 채택을 별도 단일 축 작업으로 검토한다.

## 0.10.108 릴리스 범위

`0.10.108`은 `0.10.107` 이후 수집 후 자동 정리의 데이터 안전 경계와 Public 저장소의 현재 추적 트리 안전 게이트를 보완하는 릴리스다. `VERSION`과 릴리스 기준 문서는 `0.10.108`로 맞춘다.

- 자동 정리는 새 출처 수집 전에 실행하지 않고, 사용 가능한 출처 저장이 끝난 뒤 순위 준비 직전에 실행한다.
- 모든 사용 가능한 출처가 실패하면 `skipped_source_failure`로 기존 통합 순위와 보존 자료를 유지하고 대기 중 자동 정리를 폐기하며 주제 방향 생성을 보류한다.
- 일부 출처가 `success`·`partial`·`partial_success`·`skipped`이면 성공한 결과를 보존한 채 기존 정리·순위 흐름을 계속한다.
- 직접 실행, 예약/안전 실행, 대시보드 백그라운드 실행과 Streamlit 런타임이 같은 `post_collection_cleanup_runtime` 계약을 사용한다.
- 외부 API 대기 중 DuckDB 연결을 장시간 유지하지 않는 짧은 연결 구조를 유지한다.
- Public 전환 후 지속 검사로 `python scripts/check_public_readiness.py --tracked-only`을 `main`과 `work/**` CI에 포함해 현재 추적 트리의 민감 경로 유입을 빠르게 탐지한다. 이는 push 전 Secret 차단을 대신하지 않는다.
- 관련 회귀 테스트와 `work/0.10.108` CI를 릴리스 준비 게이트로 유지하며, 실제 DB·외부 API·브라우저 세션은 자동 검증에 사용하지 않는다.

### 0.10.108 적용 후 실사용 확인

1. 정상 수집에서 `수집 → 자동 정리 → 순위/군집 → 주제 방향` 순서가 운영 로그와 실제 결과에서 유지되는지 확인한다.
2. 실제 전체 출처 장애가 발생했을 때 기존 순위·보존 자료가 유지되고 자동 정리와 주제 방향이 실행되지 않는지 확인한다.
3. 한 출처만 실패하고 다른 출처가 성공·부분 성공·변경 없음일 때 정상 결과가 취소되지 않고 후속 순위가 계속되는지 확인한다.
4. Public 저장소 운영 중 새 보호 파일이 실수로 추적되면 CI `Public tracked-tree safety check`가 실패하는지 테스트용 안전 경로에서만 확인한다. 실제 Secret은 테스트하지 않는다.

## 0.10.107 릴리스 범위

`0.10.107`은 Gemini 주제 방향 부분 응답 보강, 2단계 군집 희소 응답 계약 정합화, 결정론적 군집 baseline 읽기 전용 비교 진단, 군집 throttle 원인 분류, 적용 도구·하네스 안전성, Public 공개 준비를 누적 정리하는 릴리스다. 기존 DuckDB 데이터와 원본·자료팩·AI 기록·초안·사실 확인·발행 기록, 출처별 부분 성공, 수동 최종 발행 원칙은 유지한다.

- Gemini 주제 방향에서 HTTP 200 부분 응답의 기존 유효 결과는 그대로 유지하고 원본 배치의 누락·검증 탈락 ID만 최대 한 번 보강 요청한다.
- 2단계 군집의 `existing_links`·`new_groups`·`uncertain_nos`는 후보 번호를 서로 중복하지 않도록 하고 신규 그룹 대표 제목은 입력 문자열 재출력 대신 그룹 내부 `representative_candidate_no`로 선택한다.
- 신뢰 가능한 최신 군집 품질 표본에 결정론적 baseline 비교를 읽기 전용으로 붙이되 현재 저장 군집도 정답으로 간주하지 않고 생산 군집 규칙을 자동 변경하지 않는다.
- 최근 군집 요청 진단은 로컬 `tpm_wait_seconds`와 Gemini `rate_limited`·`daily_quota_exhausted`를 분리해 로컬 대기와 공급자 제한을 혼동하지 않는다.
- 적용 도구와 하네스는 보호 파일, PowerShell 7, 최종 단일 릴리스 커밋과 `behind 0 / ahead 1` 계약을 유지한다.
- Public 공개 준비는 현재 추적 파일뿐 아니라 Git 전체 이력·PR audit refs·Gitleaks·과거 인코딩 payload 검토를 포함한다. 릴리스 후보 준비 전에 로컬 공개 준비 검사가 `ready: True`로 확인됐다.
- `.env`, 실제 DB/WAL/잠금, Parquet, 로그, OAuth·쿠키·브라우저 인증 상태, 테스트·빌드 임시 산출물은 릴리스 대상에 포함하지 않는다.
- 자동 검증은 실제 DB·외부 API·Windows 작업 스케줄러·실사용 브라우저 세션을 대체하지 않는다.
- 릴리스 후에는 실제 데이터 표본의 주제 방향 부분 응답 보강, 군집 희소 응답·baseline·throttle 진단과 앱 supervisor 생명주기를 우선 확인한 뒤 Public 전환의 최종 확인으로 이어간다.

## 0.10.106 릴리스 완료 상태

`0.10.106`은 P2 실제 운영 진단의 신뢰성 보강과 실제 표본에서 확인된 군집 품질 문제를 한 축씩 수정한 릴리스다. NAVER·Daum 사용자 개수 상한을 제거하고 `trend_lookback_hours` 최근 시간 범위 전체를 분석하도록 맞췄으며, 현재 2단계 군집의 `50,000` 내부 스냅샷 스캔 안전 상한·외부 1회·토큰 기준 순차 요청 계약에 진단 기준을 맞췄다. 과거 고정 후보 수 작업 이력의 읽기 호환성은 유지한다. 최신 군집 작업의 저장 결과를 다시 계산하지 않고 다중 신규·기존 연결·단독 신규·미확정 후보와 실제 제목 표본으로 재구성하는 읽기 전용 품질 진단을 추가했고, 작업 원장 수치와 현재 스냅샷이 일치할 때만 재구성을 신뢰한다. 실제 로컬 품질 표본에서 서로 다른 상품인 원형파라솔과 IP2726 모니터가 `특징·선택·포인트` 같은 편집 템플릿 표현을 공유해 기존 군집 연결 대상으로 노출된 오병합 사례를 확인했고, 기존 군집 후보 인덱스가 이런 일반 템플릿 단어와 조사 결합형 표현을 식별 근거로 사용하지 않도록 단일 축 방어를 추가했다.

- 최신 데이터 수집은 별도 프로세스로 실행하고 공유 상태 파일에서 진행률·현재 단계·최신순 이력을 갱신한다.
- 실행 중에는 수집·재계산·주제 방향 버튼을 비활성화하고 완료·실패 후 다시 활성화한다.
- 출처 수집, 1차 군집, 2차 Gemini 군집, 통합 순위 계산·저장과 주제 방향을 프로그램 로그에서 구분한다.
- 일부 군집이 저장되면 미처리가 남아 있어도 현재 군집의 주제 방향 생성을 이어간다.
- 주제 방향 대상 선정 상세 로그에 전체 군집, 추천·검토, 기회 점수 통과, 기존 방향 완료, 생성 필요, 민감 제목, 근거 없음, 이번 생성 대상과 요청 범위 밖 미검사를 남긴다.
- 같은 계산의 중복 `cluster_id`와 원문 연결을 저장 전에 정리한다.
- 수집·군집 잠금은 PID 시작 식별자와 heartbeat/lease를 사용한다.
- Streamlit은 전용 포트 `8518`의 전경 supervisor에서 단일 인스턴스로 실행하며 웹 업데이트 후에도 같은 터미널이 앱을 소유한다.
- `stop_app.bat`은 등록된 supervisor·Streamlit PID와 시작 시각이 일치하는 프로세스만 종료한다.
- 기존 DuckDB 데이터, 원본, 자료팩, 초안, 사실 확인과 발행 기록은 자동 수정하지 않는다.
- `0.10.106`에 추가 기능을 더 섞지 않고 새 실제 표본의 반복 문제가 확인되면 다음 버전의 단일 축 작업으로 넘긴다.
- 릴리스 적용 도구는 깨끗한 `work/*` 브랜치에서 시작해도 사용자가 수동으로 `main`을 먼저 선택할 필요 없이 안전하게 `main`으로 전환한 뒤 기존 최종 반영 엔진을 실행하도록 보완했다. 실패 시 작업 트리가 깨끗하면 원래 작업 브랜치로 복귀한다.
- `0.10.106`은 이 보완을 포함한 최종 단일 커밋으로 `main`에 반영됐고 후속 변경은 `work/0.10.107`에서 누적했다.

## 0.10.106 적용 후 우선 확인

1. `run_app.bat` 실행 시 `http://127.0.0.1:8518`로 열리고 두 번째 실행이 중복 인스턴스를 만들지 않는지 확인한다.
2. Antigravity 터미널에서 `Ctrl+C`를 누른 뒤 8518 포트와 등록 Streamlit이 함께 종료되는지 확인한다.
3. `stop_app.bat`이 등록된 앱만 종료하고 YouTube 트렌드 트래커나 다른 Python 프로세스는 건드리지 않는지 확인한다.
4. 웹 업데이트 뒤 같은 터미널 supervisor가 앱을 8518로 다시 실행하고 이후 `Ctrl+C`로 재시작된 앱까지 종료되는지 확인한다.
5. `run_p2_diagnostics.bat` 읽기 전용 진단 전후에 실제 DB·WAL이 변경되지 않고 현재 출처·Gemini·군집 상태를 설명하는지 확인한다.
6. 다음 정상 수집·군집 뒤 `quality_sample`이 최신 작업과 현재 스냅샷이 일치할 때만 `reconstruction_reliable=true`로 표시되는지 확인한다.
7. 기존 군집 연결에서 일반 편집 템플릿만 공유하는 서로 다른 상품이 후보로 다시 노출되지 않는지 실제 제목 표본을 확인한다.
8. 실제 사용자 데이터에서 작업 대기열 → AI 요청서 → AI 결과 → 편집 → 발행 보조 흐름을 한 번 확인한다.

- 실제 요청 글감 수, 설정 상한, 사고 수준, 제한 시간과 finish reason 분포를 현재 조건과 과거 조건으로 나눠 계속 확인한다.
- 확인 완료: v6 저장 계약 완전율과 저장 원문 근거 연결은 실제 표본에서 100%였다.
- 확인 완료: 최근 출처 수집은 Gemini 실패가 출처 수집 성공을 취소하지 않는 분리 계약을 유지했다.
- 확인 완료: NAVER·Daum 전체 범위 적용 후 `selected_items = recent_items`, `outside_limit_unclustered_items = 0`이었다.
- 확인 완료: P2 2단계 군집 표본은 외부 스냅샷 1회 안에서 Gemini 요청을 토큰 기준으로 여러 번 순차 실행했고 실패 요청은 없었다.
- 구현 완료: `trend_clustering.quality_sample`은 최신 작업의 `first_stage_key`와 현재 군집·원문을 연결해 다중 신규·기존 연결·단독 신규·`retry`·`needs_review` 대표 제목을 읽기 전용으로 보여주며, 작업 집계와 군집 스냅샷이 맞을 때만 `reconstruction_reliable=true`로 표시한다.
- 확인 완료: 현재 군집 표본에서 원형파라솔과 IP2726 모니터처럼 실제 제품 식별이 전혀 다른 제목이 일반적인 `특징·선택·포인트` 표현 때문에 기존 군집 후보 경로에서 만날 수 있던 원인을 확인했다.

- 구현 완료: 신뢰 가능한 최신 품질 재구성 표본에 한해 같은 `first_stage_key` 작업 후보를 deterministic baseline으로 다시 비교하는 읽기 전용 진단을 추가했다. 안전 충돌을 먼저 차단하고 높은 제목 유사도와 공통 식별 근거가 있는 후보 쌍만 baseline 병합 후보로 잡아 현재 저장 군집과의 일치·불일치·안전 차단을 측정한다. 현재 저장 결과는 정답으로 간주하지 않으며 실제 군집·Gemini 호출·설정은 변경하지 않는다.
- 구현 완료(0.10.109): baseline 재구성 또는 비교가 불완전하면 일치·불일치 수치를 채택 근거처럼 노출하지 않고 사람용 출력에서 대표 제목과 불완전 원인을 확인할 수 있게 했다. 운영·P2 진단은 동일 품질 runtime을 재사용한다.
- 남은 판단: 이후 실제 로컬 품질 표본에서 같은 종류의 템플릿형 오병합이 재발하는지와 별도로 과분리·병합 누락이 반복되는지 확인한다. 단독 후보 비율만으로 결함을 단정하지 않는다.
- 남은 판단: 새 `deterministic_baseline` 표본의 현재 군집 대비 일치·불일치 제목을 직접 확인하고, 품질이 유지되면서 Gemini 호출·토큰을 실제로 줄일 수 있다는 근거가 생길 때만 ambiguous-only Gemini 전환을 검토한다.
- JSON 절단·구문 오류, 누락 ID, 검증 탈락, 재시도와 `MAX_TOKENS`는 현재 조건과 과거 조건을 계속 분리해 본다.
- 개별 생성이나 2단계 생성은 사용하지 않고 현재 한 묶음 처리 구조를 유지한다.

### P3. 진단 결과에 따른 단일 축 개선

상태: NAVER·Daum 사용자 분석 입력 개수 상한 제거, 군집 진단의 토큰 분할 계약 정합화, 기존 군집 후보의 일반 편집 템플릿 오병합 방어, 2단계 rate limit·로컬 TPM cooldown 원인 분류, 희소 응답 상호 배타 계약과 신규 그룹 입력 문자열 반복 출력 제거까지 단일 축으로 보완했다. 다음 개선은 새로운 실제 진단에서 반복 문제가 확인된 경우 다음 버전에서 하나를 선택한다.

- 완료: NAVER·Daum은 사용자 개수 상한 대신 최근 `trend_lookback_hours` 범위 전체를 분석하고, 기존 DB 상한 값은 삭제하지 않은 채 호환 입력으로 보존한다.
- 완료: DuckDB partitioned TopN 엔진 조건을 넘지 않도록 포털 그룹당 `999,999`개 내부 SQL 방어 경계만 유지한다. 이는 사용자 조정 상한이 아니다.
- 완료: 현재 2단계 군집 진단은 `50,000`을 Gemini 요청당 후보 수가 아닌 내부 스냅샷 스캔 안전 상한으로 해석하고 외부 작업 1회·토큰 기준 순차 분할 계약을 검사한다.
- 완료: 과거 고정 후보 수 군집 작업 이력은 기존 진단 의미를 유지해 읽을 수 있다.
- 완료: 기존 군집 후보 인덱스는 `특징`, `선택`, `포인트`, `총정리` 및 조사 결합형 표현을 식별 토큰에서 제외하고, 실제 상품·사건 식별 토큰을 공유하지 않는 후보는 Gemini 기존 군집 선택지로 올리지 않는다.
- 완료: 최근 2단계 요청 메트릭에서 로컬 TPM 대기와 Gemini rate limit·일일 quota를 분리 표시하며 로컬 대기만으로 공급자 오류를 판정하지 않는다.
- 완료: `existing_links`·`new_groups`·`uncertain_nos`는 같은 `candidate_no`를 중복 반환하지 않는 상호 배타 범주임을 프롬프트에 명시했다. 파서의 기존 보수적 중복 검증은 유지해 규칙 위반 응답을 자동 병합하지 않는다.
- 완료: `new_groups`는 입력 제목 문자열 대신 그룹 안의 `representative_candidate_no`만 반환한다. 파서는 선택 번호가 그룹 구성원인지 검증하고 원본 제목을 내부 `representative_title`로 복원한다.
- 진단 완료: deterministic baseline 비교 경로는 구현했지만 생산 군집에 채택하지 않았다. 다음 실제 신뢰 가능 표본에서 현재 결과와의 일치·불일치 제목을 검토한 뒤 별도 단일 축 작업으로 채택 여부를 결정한다.
- 원칙 유지: 군집 개선은 Gemini 안정성 판단 이후 실제 반복 품질 문제가 확인된 한 축에만 적용한다.
- 후보: 제목 정규화와 군집 후보 탐색 범위의 추가 문제
- 후보: 전역 군집 임계값 조정
- 후보: Google Trends 강제 연결 또는 별도 처리

처리량·사고 수준·프롬프트·파서·군집 기준을 동시에 변경하지 않는다. 같은 버전에서 여러 축을 섞지 않고 동일 표본에서 개선률·오군집·실행 시간을 비교한다.

### P3-보조. 1·2차 통합 군집 실사용 비교

상태: 구현 완료·실사용 품질 비교 진행 중. 실제 P2 표본에서 현재 토큰 분할 실행 계약을 확인했고 읽기 전용 제목 표본 진단도 구현했다. 첫 명백한 품질 문제인 일반 편집 템플릿 기반 기존 군집 오병합의 원인 경로를 차단했으며, 이후 실사용 표본에서 재발 여부와 다른 품질 문제를 한 축씩 확인한다.

- 1차 군집은 날짜·회차·제품·행동·방향 충돌을 `must_split`으로 처리한다.
- 동일 회차·동일 제품과 행동·안전한 동일 제목처럼 강한 근거가 있을 때만 `must_merge`를 적용한다.
- 확실한 병합 근거도 충돌도 없으면 `undetermined`로 2차에 전달한다.
- 2차 요청은 실제 `trend_*` ID 대신 로컬 `option_id`를 사용한다.
- 희소 응답의 `existing_links`·`new_groups`·`uncertain_nos`는 후보 번호를 서로 중복하지 않고, 중복 응답은 기존 파서가 불확실 대상으로 보존한다.
- 신규 그룹의 대표 제목은 Gemini가 그룹 안의 `representative_candidate_no`를 고르고 프로그램이 해당 원본 제목을 복원하므로 입력 제목 문자열을 응답에 반복하지 않는다.
- 신뢰 가능한 최신 품질 표본에는 같은 작업 후보를 대상으로 한 `deterministic_baseline` 비교 결과가 붙으며, 이 수치는 현재 저장 군집과의 비교일 뿐 품질 정답률로 사용하지 않는다.
- 범위를 벗어난 option, 규칙 충돌, 낮은 신뢰도와 누락은 자동 저장하지 않는다.
- 기존 군집 후보는 일반 편집 템플릿 표현만 공유해서는 생성하지 않고 실제 식별 토큰을 공유해야 한다.
- 한 작업은 미처리 스냅샷을 한 번 준비하며 `50,000`은 요청당 후보 수가 아니라 내부 스캔 안전 상한이다.
- 제목·사건·식별·기존 군집 관점은 입력 토큰 목표와 TPM에 맞춰 필요한 수만큼 나누고 한 요청씩 순차 실행한다.
- 읽기 전용 품질 표본은 후속 군집 계산으로 현재 스냅샷이 바뀌었으면 당시 결과라고 추정하지 않고 `reconstruction_reliable=false`로 표시한다.
- 미처리 자료가 없을 때 Gemini 호출 없이 0배치 성공으로 끝나는지 확인한다.
- 작업 로그의 현재 단계·남은 미처리와 실제 Gemini 요청 수·TPM 대기·토큰을 확인한다.
- 작업 중 다른 탭의 설정·글감·초안 조회가 DuckDB 잠금 없이 열리는지 확인한다.

## 1·2차 통합 군집 안전성 실사용 검증 우선순위

5. `option_id`가 허용된 실제 후보로만 변환되는지 확인
6. 기존 군집 연결에서 일반 편집 템플릿만 공유하는 서로 다른 상품이 후보로 다시 나타나지 않는지 확인
7. 불확실·충돌·검토 전환과 기존 연결·신규 군집 품질 비교
8. deterministic baseline의 현재 저장 군집 대비 일치·불일치·안전 차단 제목 표본 확인
9. 현재 단계·남은 미처리·요청별 진행률의 화면 갱신 확인
10. 입력·출력·사고·전체 토큰, TPM 대기와 처리량 확인
11. 동시 화면 조회가 DuckDB 잠금 없이 유지되는지 확인

## 후속 복구 정책

- 구현 완료: 새 수집 이력을 시작할 때 오래된 `running` 행을 자동 `failure`로 바꾸지 않고 원본 상태를 보존한다.
- 구현 완료: 6시간 이상 `running`으로 남은 이력은 수집·군집 잠금의 PID 시작 식별자와 heartbeat/lease가 모두 현재 활성 상태를 뒷받침하지 않을 때 화면에서만 `상태 확인 필요`로 표시한다.
- 잠금 상태를 읽지 못한 경우에는 추정으로 `상태 확인 필요`를 붙이지 않고 기존 `실행 중` 표시를 유지한다.
- 실제 이력 행을 자동 `UPDATE`하는 복구는 기준 시간·사용자 확인·기존 기록 보존 정책을 별도로 설계한 뒤에만 검토한다.
- 잠금 파일이 없거나 PID가 다른 프로세스에 재사용된 경우에도 실제 DB·작업 이력을 추정으로 완료·실패 처리하지 않는다.
- 실제 로컬 이력 표본에서 오래된 중단 기록과 현재 정상 실행이 기대한 표시로 구분되는지는 수동 확인 대상으로 남긴다.

## P8. 발행 성과 기록과 추천 규칙 조정 (구현 완료·실사용 검증 대기)

- 발행 후 7일·30일·90일 수동 성과 스냅샷과 동일 구간 발행처 비교를 확인한다.
- 표본이 적을 때 추천 규칙을 자동 변경하지 않는다.

## 안전 원칙

- 실제 DB는 읽기 전용 진단이 명시된 작업 외에는 자동 검증에 사용하지 않는다.
- `.env`, API 키, 실제 DB·WAL·잠금, Parquet, 로그와 브라우저 인증 상태를 외부에 전달하거나 커밋하지 않는다.
- 한 출처나 Gemini 후처리 실패가 다른 출처의 정상 수집 결과를 취소하지 않게 한다.
- 자동 로그인, 쿠키 저장, CAPTCHA 우회와 무인 자동 게시를 추가하지 않는다.
- 여러 설정을 동시에 바꾸지 않고 실제 표본에서 확인된 한 축만 다음 작업으로 선택한다.

## 후속 기능 후보 — 0.10.106 이후 검토

Content Trend Tracker에 직접 흡수할 가치가 높은 후속 기능 후보를 기록한다. 이 항목은 구현 확정이 아니며, 기존 실사용 검증과 안정화보다 우선하지 않는다.

1. **Deterministic Baseline + ambiguous-only Gemini**
   - 읽기 전용 비교 진단 구현 완료: 신뢰 가능한 최신 군집 작업의 1차 후보를 안전 충돌 차단 + 높은 제목 유사도·공통 식별 근거 baseline으로 비교한다.
   - 현재 저장 군집과의 일치·불일치·안전 차단을 표시하지만 현재 결과도 정답으로 간주하지 않는다.
   - 실제 표본에서 품질이 동일하거나 개선되면서 Gemini 호출 수·토큰·처리 시간이 줄어들 근거가 확인된 경우에만 생산 경로 채택을 별도 검토한다.
   - 처리량·프롬프트·파서·군집 기준을 동시에 바꾸지 않고 채택 시에도 한 축 실험으로 진행한다.

2. **OutcomeEvaluation — 발행 성과 피드백 루프**
   - 글감 선정 당시 점수·출처·주제 방향과 실제 발행 후 7일·30일·90일 성과를 연결해 선정 규칙의 실제 효과를 비교한다.
   - 표본이 충분히 쌓이기 전에는 추천 규칙을 자동 변경하지 않는다.
   - `P8 발행 성과 기록`의 기존 데이터를 우선 재사용하고 별도 중복 저장 구조는 만들지 않는다.

3. **CanonicalEntity — 동일 대상 alias 정규화**
   - `OpenAI / Open AI / 오픈AI`처럼 같은 대상을 가리키는 표현 때문에 과분리가 반복되는 실제 표본이 확인될 때만 도입을 검토한다.
   - 초기 범위는 `canonical_name`, `aliases`, `entity_type`, `external_ids` 수준으로 제한하고 거대한 범용 entity DB를 만들지 않는다.

4. **Source Registry + SourceHealth**
   - 새 출처를 늘리기 전에 기존 출처별 `last_success_at`, freshness lag, schema fingerprint, 연속 실패와 fallback 상태를 진단 가능한 형태로 통합할 가치가 있는지 검토한다.
   - 공식 API/RSS/공개 데이터 우선, 실제 연결 시점에 Terms·데이터 권리·무료 한도·rate limit을 다시 확인한다.

5. **Meaningful Change 패턴과 provenance 보강**
   - 기존 중요 주제에 의미 있는 새 변화가 생겼는지 `fetch → normalize → diff → deterministic condition → optional AI` 패턴을 후속 콘텐츠 탐지에 제한적으로 재사용할 수 있는지 검토한다.
   - 대규모 연구 보관 시스템을 별도로 만들지 않고 `content_hash`, 확인 시점/freshness, 과거 검증 근거 재사용 같은 데이터 원칙만 필요한 범위에서 흡수한다.
   - AI 출력 공통 정규화 도구는 JSON/포맷 실패가 실제로 반복될 때만 다시 검토한다.

우선순위는 `0.10.109` 수집·정리 진행 상태 실사용 확인 → deterministic baseline 실제 표본 비교·채택 판단 → 충분한 발행 성과 표본이 쌓인 뒤 OutcomeEvaluation 순으로 둔다.
