# 콘텐츠 트렌드 트래커

콘텐츠 트렌드 트래커는 YouTube, NAVER, Daum, Google Trends, Wikimedia 신호를 수집·정규화·군집화해 정보성 글감 후보를 만들고, 근거 검토부터 수동 발행 보조까지 이어 주는 로컬 Streamlit 프로그램입니다.

## 현재 버전 확인

앱을 실행하면 모든 화면의 상단에 `현재 버전: vX.Y.Z`가 표시되고 브라우저 탭 제목에도 같은 버전이 나타납니다. 표시 기준은 프로젝트 루트의 `VERSION` 파일 하나이며, 파일이 없거나 형식이 잘못돼도 앱은 중단되지 않고 `버전 확인 불가`로 표시됩니다.

## 현재 제작 흐름

```text
외부 출처 수집
  ↓
원문 저장·중복 갱신
  ↓
유사 주제 군집화·점수 계산
  ↓
Gemini 글감 분석 또는 사용자 검토
  ↓
AI 요청서·자료팩 생성
  ↓
AI JSON 형식·출처 검사
  ↓
초안 편집·리비전·사실 확인
  ↓
발행처 배정·SEO 준비·Chrome/Blogger 초안 보조·사용자 수동 발행·성과 기록
```

프로그램은 자동 로그인, 쿠키 저장, CAPTCHA 우회, 게시 버튼 자동 클릭을 수행하지 않습니다.

## 티스토리 발행 보조 순서

티스토리는 설정의 `발행 채널 → 🟠 티스토리 1`에서 `내 티스토리 블로그 주소`만 저장합니다. 프로그램이 개인 블로그의 `/manage/newpost` 주소를 자동으로 만들며, 로그인되어 있으면 새 글 편집기로 바로 이동합니다.

```text
1. SEO·이미지 준비 저장
2. Chrome 전달 데이터 복사
3. 티스토리 글쓰기 바로 열기
4. 확장에서 불러오기 → 입력칸 진단 → 현재 편집기에 입력
5. 제목·본문·태그를 직접 확인하고 사용자가 저장·발행
```

로그인 화면이 나오거나 다른 페이지가 열릴 때만 도움말을 펼쳐 로그인 보조 버튼과 주소 점검 순서를 사용합니다.

## 플랫폼별 글쓰기 연결 방식

설정의 `발행 채널`에서는 로그인 주소를 따로 입력하지 않습니다.

- Blogger 3개: 각 블로그에서 `새 글`을 연 뒤 주소창의 **Blogger 새 글 편집기 주소**를 프로필별로 저장합니다.
- 네이버 1개: 네이버 블로그에서 `글쓰기`를 연 뒤 주소창의 **네이버 새 글 편집기 주소**를 저장합니다.
- 티스토리 1개: **내 티스토리 블로그 주소**만 저장하면 프로그램이 `/manage/newpost`를 자동으로 연결합니다.

설정 상단의 `연결 준비도`는 전체 연결과 Blogger·네이버·티스토리별 완료 수를 표시하고, 미설정과 주소 형식 오류를 구분합니다. 진단은 저장된 주소 형식만 읽으며 외부 접속이나 로그인은 수행하지 않습니다. 준비 완료는 실제 편집기 이동 성공을 보증하지 않으므로 발행 보조에서 직접 확인합니다.

발행 보조에서는 준비값 저장만 `조건부`이며, `필수 ② 전달 데이터 복사 → 필수 글쓰기 바로 열기 → 확장에서 불러오기·진단·입력 → 직접 확인 후 저장·발행` 순서로 진행합니다. 개별 복사와 진단 도구는 선택 영역에 접혀 있습니다.

## 설정 화면 구성

설정 화면은 `기본 설정 / AI·품질 / 발행 채널 / 자동화·이력 / 데이터·연동` 순서로 나뉩니다. 이전처럼 진단과 백업 화면이 탭 위에 먼저 길게 표시되지 않습니다.

- `AI·품질 → 품질·운영 진단`: Gemini 생성 안정성, 수집 출처 다양성, 군집 실패·단일 출처 사례와 주제 방향 v6 진단
- `데이터·연동 → 백업·복구`: 현재 DB 무결성 검사, 수동 백업, 백업 검사와 명시적 확인 복구

상위 메뉴와 보조 탭은 가운데 정렬하고 버튼 최소 폭을 12.5rem으로 유지합니다. 긴 문구는 줄바꿈하지 않으며 화면이 좁으면 가로로 스크롤합니다. 선택하지 않은 설정 영역은 렌더링하지 않습니다.

## 동일 고유 회차 군집 처리

`로또 1235회`, `제1235회 로또`처럼 같은 대상·같은 긴 회차를 가리키는 제목은 출처별 부가 문구가 달라도 하나의 군집 후보로 비교합니다. `제1235회` 표기는 `1235회`로 정규화하며, 3자리 이상 `회·차` 식별자는 반복 빈도가 높아도 후보에서 누락하지 않습니다.

다른 회차와 서로 다른 대상은 계속 분리합니다. 기존 원본 신호를 합치거나 삭제하는 것이 아니라 순위 계산 시 `trend_clusters`와 연결 결과만 새 규칙으로 다시 만듭니다.

## Gemini 글감 자동 분석

현재 운영 기준:

- 요청당 기본값: **글감 15개**, 허용 상한: **30개**
- 기본 동시 요청 수: **1개**
- 기본 실행 한 번의 최대 처리량: **15개**
- 글감 기회 점수 기본 기준: **50점 이상**
- 글감 분석 사고 수준 기본값: **medium**
- 글감 분석 요청 제한 시간 기본값: **600초(10분)**
- 저장되지 않은 후보는 삭제하지 않고 다음 실행 대상으로 유지
- Gemini 실패가 출처 수집 성공을 취소하지 않음

`.env`에 30보다 큰 값을 넣어도 프로그램은 요청당 30개로 제한합니다. 예약·BAT 실행은 기본적으로 한 묶음만 처리합니다.

과거 기본값 `360초`는 `600초`로 자동 보정합니다. 사용자가 360초가 아닌 별도 값을 지정한 경우에는 그 값을 유지하며, 최대 허용값은 900초입니다.

```env
GEMINI_TOPIC_ANGLE_ITEMS_PER_REQUEST=15
GEMINI_TOPIC_ANGLE_MAX_PARALLEL_REQUESTS=1
GEMINI_TOPIC_ANGLE_REQUEST_STAGGER_SECONDS=5
GEMINI_TOPIC_ANGLE_TIMEOUT_SECONDS=600
GEMINI_TOPIC_ANGLE_MIN_OPPORTUNITY_SCORE=50
GEMINI_TOPIC_ANGLE_THINKING_LEVEL=medium
```

예약 수집의 Gemini 단계는 다음 순서로 동작합니다.

```text
분석 대상 조회
  ↓
DuckDB 연결 종료
  ↓
Gemini API 호출·응답 검증
  ↓
DuckDB를 다시 짧게 열어 유효한 결과만 저장
```

응답 일부가 검증을 통과하지 못하면 유효한 글감만 저장하고 나머지는 다음 실행 대상으로 남깁니다. 10분으로 늘린 뒤에도 데이터가 덜 정리돼 보이면 최근 3~5회 실행의 요청 글감 수, 저장 글감 수, 실패 배치, 검증 오류와 응답 원문을 확인한 뒤 프롬프트·파서·항목 수를 별도 조정합니다. 시간 연장과 군집·검증 기준 변경을 동시에 적용하지 않습니다.

## Gemini 생성 안정성·설정 추천

설정 화면에서 최근 Gemini 글감 분석 기록을 읽어 저장률, 부분 성공·실패, 재시도, 응답 검증 실패, 생성 토큰과 소요 시간을 확인합니다. 각 API 시도에는 호출 당시의 실제 요청 글감 수·설정 상한·사고 수준·제한 시간과 Gemini 종료 사유를 기록하며, `MAX_TOKENS` 종료를 일반 응답 검증 실패와 별도로 표시합니다. 기존 호출에는 새 실행 조건이나 종료 사유가 없을 수 있습니다.

진단은 실제 런타임의 요청당 처리량과 사고 수준을 표시하며, 현재 처리량 유지 또는 실제 런타임보다 낮은 안전 상한을 권고합니다. 호출 기록 확장은 외부 API 호출 수, 요청 프롬프트, 응답 JSON 스키마와 처리량을 변경하지 않습니다.

처리량을 줄이기 위한 최소 표본은 **완료 실행 3회·요청 글감 60개**입니다. 그보다 적으면 표본 부족으로 표시하고 현재 런타임 처리량을 유지합니다.

추천은 읽기 전용입니다.

- 모델·처리량·사고 수준을 자동 변경하지 않음
- 사고 수준은 현재 런타임 값(`minimal`·`low`·`medium`·`high`) 유지 권고
- `trend_topic_angle_batch_v1` 글감 분석만 집계
- Gemini 직접 초안 생성은 추천 계산에서 제외
- 외부 API를 새로 호출하지 않음

## 주제 방향 v6 품질·운영 진단

설정 화면의 `주제 방향 v6 품질·운영 진단`은 0.10.86 이후 새 방향 계약의 저장 품질과 운영 표본을 읽기 전용으로 확인합니다.

- v6 글감·방향 수와 글감당 3방향 완성 여부
- 검색 의도·독자 질문·수요 근거·점수 이유의 필수값 확인
- 하위 점수 범위·총점 일치와 점수순 저장 여부
- 방향에 연결된 원문 ID가 현재 원문 테이블에 존재하는지 확인
- v6 성공 요청 수·요청 글감 누계·현재 실행 조건 일치 여부
- 응답 검증 실패·재시도·생성 토큰·소요 시간 확인
- 현재 분석 완료·대기 글감과 대기 해소 예상 실행 횟수

v6 호출은 `gemini_api_calls.feature_version`으로 이전 계약과 구분합니다. 기존 호출은 버전이 비어 있을 수 있습니다. 최소 운영 표본은 성공 요청 4회·요청 글감 60개입니다. 외부 API를 호출하거나 설정·방향·원문을 자동 변경하지 않습니다. 표본이 부족하거나 문제가 보여도 진단 화면이 처리량·사고 수준·프롬프트·군집 기준을 자동 변경하지 않습니다.

## 수집 출처 다양성 진단

설정 화면의 `수집 출처 다양성 진단`은 기본 접힘 상태이며, 최근 원문과 현재 순위 군집을 읽기 전용으로 비교합니다.

- 최근 24시간·72시간·7일 중 진단 범위 선택
- 최근 수집 원문과 현재 군집 연결 원문 수 확인
- 전체 군집 중 서로 다른 출처가 2개 이상 섞인 비율 확인
- 단일 출처 군집과 3개 이상 출처 군집 수 확인
- 출처별 원문 연결률·교차 출처 연결률·군집 점유율 확인
- 자주 함께 묶이는 출처 조합 확인
- 최근 데이터가 없는 출처와 특정 출처 편중 확인
- Google Trends처럼 검색어형 신호가 다른 출처와 잘 연결되지 않는 경우 점검 순서 안내

운영 판단 기준은 군집 20개 미만을 표본 부족으로 보고, 다중 출처 군집 비율 5% 미만을 매우 낮음, 15% 미만을 개선 필요, 30% 미만을 관찰로 표시합니다. 이 기준은 화면 안내용이며 수집 설정, 분석 입력 상한, 제목 정규화 또는 군집 유사도 기준을 자동으로 변경하지 않습니다.

원문 연결률이 낮아도 수집 실패라고 단정하지 않습니다. 분석 출처별 입력 상한, 오래된 게시물·탐색 페이지 제외, 품질 필터와 현재 순위 계산 범위 때문에 군집에 포함되지 않은 원문이 있을 수 있습니다. 실제 기준 변경은 진단 결과와 로컬 데이터 확인 후 별도 작업으로 진행합니다.

## 군집 실패·단일 출처 사례 상세 보기

설정 화면의 `군집 실패·단일 출처 사례 상세 보기`는 기본 접힘 상태입니다.

- 최근 24시간·72시간·7일의 군집 밖 원문 확인
- 단일 출처로만 구성된 군집 확인
- 출처·제목·예상 원인 검색
- 다른 출처가 포함된 가장 유사한 기존 군집 후보 확인
- 유사 후보, 현재 제목 유사도, 공통 핵심어와 시간 차이 확인
- 원문 제목과 현재 정규화 제목 비교
- Google Trends 검색어형 단독 사례 확인
- 유사 후보 없음, 공통 핵심어 부족, 현재 72% 병합 기준 미달, 시간 차이, 분석 입력 상한·필터·재계산 시점 가능성 구분

사례 화면은 군집을 자동 병합하지 않습니다. 표시 원인은 확정 판정이 아니라 다음 로컬 Agent 분석 대상을 좁히기 위한 추정입니다. 후보 유사도가 높아도 날짜·회차·제품명·금액과 사건 맥락이 다르면 합치면 안 되므로 반대 사례를 함께 검토해야 합니다.

## 콘텐츠 작업 대기열

오늘의 트렌드 첫 화면에는 저장된 작업의 다음 행동을 주제별 한 건으로 표시합니다.

- 자료 보완
- AI 요청서 준비
- AI 결과 대기
- 초안 편집
- 사실 확인
- 발행 준비

첫 화면을 과도하게 차지하지 않도록 `AI 요청서 준비 N개 보기`를 기본 접힘 상태로 표시합니다. 펼치면 각 주제의 이어서 하기 버튼을 사용할 수 있고, 각 항목의 `수집 근거 보기`도 안쪽에서 기본 접힘 상태로 유지됩니다. AI 결과 대기·편집·사실 확인·발행 준비 작업은 기존처럼 바로 표시합니다.

AI 요청서 준비 항목의 수집 근거에서는 다음을 읽기 전용으로 확인할 수 있습니다.

- 연결된 트렌드 신호 전체 개수
- 최근 연결 신호 최대 8개의 출처·제목·게시 또는 관측 시각·신호값·포착 횟수·URL
- 사용자가 추가한 사실 참고 자료의 종류·제목·발행처·게시일·메모·URL

근거 데이터는 이 영역에서 수정하지 않습니다. 7일 이상 활동이 없는 작업은 방치 주의로 표시합니다.

## 자료팩 버전 비교·입력값 재사용

AI 요청서 화면 아래의 `자료팩 버전 기록·비교·입력값 재사용`은 기본 접힘 상태입니다.

- 같은 주제에 저장된 자료팩 버전과 생성 시각 확인
- 각 자료팩을 사용한 AI 결과·초안 개수 확인
- 독자 대상·글 목적·관점·카테고리·목표 분량·작성 규칙 비교
- 트렌드 신호와 사실 참고 자료의 추가·제외 내역 확인
- AI 요청서의 줄 단위 차이와 추가·삭제 줄 수 표시
- 선택한 과거 자료팩 설정을 현재 AI 요청서 입력값으로 불러오기

자료팩 원본은 수정하거나 삭제하지 않습니다. 과거 설정을 불러오는 것만으로 새 자료팩이 생성되지 않으며, 사용자가 입력값과 근거를 검토한 뒤 요청서 저장을 완료해야 다음 버전이 만들어집니다.

과거 자료팩에 포함됐지만 현재 주제 연결에서 빠진 트렌드 신호와 보관된 사실 참고 자료는 자동으로 제외하고 개수를 안내합니다. 기존 AI 생성 결과와 초안은 생성 당시 사용한 자료팩 버전에 계속 연결됩니다.

## AI 생성 결과 기록·현재 규칙 재검사

AI 요청서 화면 아래의 `AI 생성 결과 기록·현재 규칙 재검사`는 기본 접힘 상태입니다.

- 저장된 AI 생성 시각·제공자·원본 자료팩·연결 초안 확인
- 저장 당시 형식·출처 검사 결과 확인
- 현재 파서와 출처 규칙으로 같은 원문을 다시 검사
- 저장 당시와 현재의 통과 여부·오류·경고·스키마 차이 확인
- 저장된 AI 원문과 파싱 JSON 읽기 전용 확인
- 선택한 원문을 `AI 결과 가져오기` 입력란에서 다시 열기
- 연결된 초안 편집 화면으로 이동

현재 규칙 재검사는 기존 `generation_sessions`, 자료팩, 초안과 사실 확인 항목을 수정하지 않습니다. 원문 다시 열기도 Streamlit 입력란에 값을 채울 뿐 새 생성 기록이나 초안을 자동 저장하지 않습니다.

원문을 바꾸지 않고 다시 저장하면 기존 멱등성 규칙에 따라 이미 저장된 생성 기록과 초안을 재사용할 수 있습니다. 원문을 수정한 경우에는 사용자가 형식·출처 검사를 다시 실행하고 저장해야 새 기록이 생성됩니다.

## 초안 리비전 비교·안전 복원

글 편집 화면 아래의 `초안 버전 기록·비교·복원`은 기본 접힘 상태입니다.

- 저장된 리비전 번호·저장 시각·수정 메모 확인
- 선택한 과거 버전과 현재 편집본의 제목·요약·카테고리·태그 비교
- Markdown 본문 줄 단위 차이와 추가·삭제 줄 수 표시
- 긴 차이는 화면 성능을 위해 일부만 표시
- 체크박스와 `복원` 확인 문구를 모두 입력한 경우에만 복원

복원은 과거 리비전을 덮어쓰지 않습니다. 현재 편집본에 리비전으로 저장되지 않은 변경이 있으면 `복원 전 현재 편집본 자동 보존` 리비전을 먼저 만들고, 선택한 과거 내용을 다시 새 리비전으로 저장합니다.

기존 리비전, 출처, 이미지 지시와 사실 확인 기록은 삭제하지 않습니다. 복원 후 주제 상태는 편집 중으로 돌아가며, 기존 사실 확인 상태가 복원된 본문과 맞는지 사용자가 다시 검토해야 합니다.

## 사실 확인 변경 이력·안전 되돌리기

글 편집 화면 아래의 `사실 확인 변경 이력·안전 되돌리기`는 기본 접힘 상태입니다.

- 사실 확인 상태·확인 메모·근거 URL의 변경 전후 보존
- 변경 시각과 변경 사유 확인
- 주장별 전체 변경 목록 확인
- 체크박스와 `되돌리기` 확인 문구를 모두 입력한 경우에만 직전 상태로 복원
- 되돌리기 작업도 새 변경 이력으로 저장

기능을 처음 연 시점의 현재 사실 확인 상태를 기준점으로 자동 보존합니다. 기능 도입 이전의 변경 내용은 역산하지 않으며, 기준점 이후의 수정부터 변경 전후를 확인할 수 있습니다.

되돌리기는 초안 본문을 자동으로 바꾸지 않습니다. 기존 사실 확인 항목과 과거 이력은 물리 삭제하지 않으며, 되돌린 뒤 주장·본문·근거가 서로 일치하는지 다시 검토해야 합니다. 발행 전 주제는 사실 확인 상태에 따라 `editing` 또는 `publish_ready`로 다시 계산하고, 이미 발행된 주제의 발행 상태는 임의로 해제하지 않습니다.

## 블로그 발행 워크플로

발행 보조 화면은 같은 본문을 여러 곳에 자동 복제하지 않고 글감마다 전문 발행처 하나를 정해 준비하도록 구성되어 있습니다.

관리형 추천 전략 4개와 실제 활성 프로필 5개:

1. 생활자료 · Blogger · 파란색
2. IT 사용법 · Blogger · 파란색
3. 요즘 화제 · Blogger · 파란색
4. 네이버 국내 장소·서비스·경험 · 네이버 블로그 · 녹색
5. 기존 연결을 우선하는 티스토리 1개 · 주황색

Blogger 3개와 네이버 1개는 글감 추천에 사용하는 관리형 전략이며, 티스토리 1개는 실제 연결과 사용자 수동 선택을 위한 프로필입니다. 그 밖의 이전·중복 프로필은 과거 기록 보호를 위해 비활성 보관하고 활성 발행처 목록에는 표시하지 않습니다.

주요 기능:

- 제목·카테고리·태그·요약·본문을 이용한 추천 발행처와 추천 이유 표시
- 사용자 변경 배정 보존과 기존 프로필·주소 재사용
- 발행처별 SEO 제목·메타 설명·핵심 키워드와 이미지 3개 배치 계획
- 제목·본문·태그·메타 설명·전체 발행 패키지 복사
- 사용자가 실행한 현재 Chrome 탭에만 입력하는 Manifest V3 확장 프로그램
- 선택자·same-origin iframe·입력 성공 여부를 확인하는 개인정보 제한 호환성 보고서
- Blogger 공식 API의 비공개 초안 생성과 동일 내용 중복 전송 방지
- 발행 후 7일·30일·90일 수동 성과 스냅샷과 동일 구간 발행처 비교

Chrome 확장 프로그램은 `activeTab`, `scripting`, `clipboardRead`만 사용하며 로그인 정보·쿠키·브라우저 프로필을 저장하지 않습니다. 네이버·티스토리·Blogger의 최종 임시저장·공개 발행은 사용자가 직접 수행합니다. Blogger API 경로도 `posts.insert(isDraft=true)`만 사용하며 공개 게시 전환은 지원하지 않습니다.

성과 비교는 프로필당 최소 3개 글과 비교 가능한 발행처 2곳이 같은 관찰 구간에 쌓이기 전에는 표본 부족으로 표시합니다. 충분한 표본이 생겨도 추천 규칙을 자동 변경하지 않고 참고 지표만 제공합니다.

## 부분 성공과 DuckDB 안전

외부 API와 파일 읽기 중에는 DuckDB 연결을 장시간 유지하지 않습니다.

```text
짧은 설정·대상 조회
  ↓
DB 연결 종료
  ↓
외부 요청·파일 읽기·계산
  ↓
출처별 짧은 저장
  ↓
최종 순위 트랜잭션 반영
```

한 출처가 실패해도 다른 출처의 정상 결과는 저장합니다. 같은 URL·외부 ID를 다시 수집하면 행을 계속 추가하지 않고 포착 시각과 횟수를 갱신하며, 원문의 게시 시각을 재수집 시각으로 덮어쓰지 않습니다.

## DuckDB 백업·안전 복구

설정 화면에서 현재 DB 무결성을 검사하고 수동 백업을 만들거나 보관된 백업으로 복구할 수 있습니다.

- 백업 위치: 프로젝트 루트 `backups` 폴더
- 수동 백업: 최근 10개 보관
- 복구 전 자동 백업: 최근 5개 보관
- 백업 전 `CHECKPOINT`와 DB 연결 종료
- 임시 복사본을 읽기 전용으로 다시 열어 검사
- 복구 전 현재 DB를 `pre_restore` 백업으로 자동 보존
- 복구 후 추가형 호환 마이그레이션과 무결성 검사
- 활성 수집 잠금, DB 파일 점유 또는 비어 있지 않은 WAL이 있으면 변경 없이 중단

복구는 체크박스와 `복구` 확인 문구를 모두 요구하며, 프로그램이 `backups` 폴더에 만든 DuckDB만 선택할 수 있습니다. 백업 파일은 Git과 안전 업로드 ZIP에서 제외됩니다.

## 자동 수집 스케줄러

새 DB의 자동 수집 기본 입력값은 **180분**입니다.

- 180분이면 약 3시간마다 실행
- 하루 약 8회 실행
- 화면 수동 작업과 예약 BAT는 `data/trend_refresh.lock`을 공유
- 중복 실행은 외부 API를 호출하지 않고 정상 생략
- 수집·군집화 이후 Gemini 글감 분석 한 묶음을 실행
- Gemini 네트워크 대기 중 DuckDB 연결을 유지하지 않음
- 유효한 AI 결과만 저장하고 미저장 글감은 다음 실행 대상으로 유지

기존 DB 저장값과 이미 등록된 Windows 작업은 자동으로 바꾸지 않습니다. 설정 화면에서 저장하고 `스케줄 등록·변경`을 실행해야 실제 Windows 작업이 갱신됩니다.

## Gemini API 모델·기능별 사용 로그

설정 → AI·품질의 `Gemini API 모델·기능별 사용 로그`에서 최근 30일 동안 프로그램이 실제로 호출한 Gemini 기록을 모델과 기능별로 확인할 수 있습니다. `gemini-3.6-flash` 자동·예약 글감 분석과 `gemini-3.5-flash-lite` AI 2단계 군집화는 별도 행으로 표시되며 호출 수, 성공·실패, 요청 항목 수, 입력·출력·사고·전체 토큰과 최근 호출 상세를 보여줍니다.

이 화면은 로컬 `gemini_api_calls` 기록을 읽는 진단입니다. 캐시 적중과 API 키가 없어 호출 자체를 건너뛴 경우는 실제 외부 호출 수에 포함하지 않습니다. Google AI Studio 계정의 공식 남은 RPM·RPD·결제 사용량은 Google 화면에서 별도로 확인해야 합니다.


## 설정 진단 DuckDB 연결

설정 → AI·품질의 Gemini 안정성·모델별 사용 로그와 수집 출처 다양성 진단은 Streamlit 앱이 이미 열어 둔 DuckDB 연결을 재사용합니다. 같은 DB 파일을 `read_only=False`와 `read_only=True`처럼 서로 다른 구성으로 다시 열지 않으므로 `Can't open a connection to same database file with a different configuration` 오류가 발생하지 않습니다.

진단 서비스는 재사용한 연결에서 조회 쿼리만 실행합니다. 앱 연결 없이 진단 함수를 독립적으로 실행하는 테스트·도구 경로에서는 기존처럼 별도의 읽기 전용 연결을 열며, DB 스키마나 사용자 데이터를 변경하지 않습니다.


## 설정 탭 스크롤과 예약 실행 실제 상태

설정 화면의 탭 목록은 가로로 스크롤할 수 있지만 탭 본문은 별도 높이로 가두지 않습니다. 긴 모델 설정·예약 실행·데이터 연동 화면도 브라우저 세로 스크롤로 마지막 항목과 저장 버튼까지 내려갈 수 있으며 설정 화면에는 충분한 하단 여백을 둡니다.

자동화·이력의 예약 실행 화면은 Windows 작업 스케줄러의 등록·준비 상태와 별도로 최근 `background_refresh` DB 기록을 표시합니다. 최근 시작 시각, 신규·갱신 자료 수, 외부 요청 수, 출처별 성공·생략·실패와 오류를 확인할 수 있습니다.

예약 수집이 성공해도 외부 결과가 이전과 같으면 신규·갱신 건수가 0일 수 있습니다. 또한 새로 주제 방향을 만들 대상이 없으면 Gemini 단계가 `생략·변경 없음`으로 기록되고 Gemini API 호출 로그의 최근 시각도 바뀌지 않습니다. 실제 이상 여부는 Windows 작업 상태가 아니라 최근 예약 실행 DB 기록과 출처별 상세를 기준으로 판단합니다.


## 1차 정리·Flash-Lite 2차 군집화

`저장 자료 정리·순위 다시 계산`은 최근 미처리 원문을 최대 4,000개까지 읽어 같은 정규 URL과 안전한 완전 동일 제목을 먼저 1차 군집으로 만듭니다. 추적 쿼리만 제거한 URL을 비교하며 날짜·회차·제품·금액·주가 방향 같은 명백한 사실이 충돌하면 같은 URL이나 제목이어도 분리합니다.

1차 군집은 `gemini-3.5-flash-lite`에 요청당 최대 200개씩 전달됩니다. Flash-Lite는 새 1차 군집을 앞선 배치에서 완료된 2차 군집에 연결하거나, 같은 배치 안에서 새 2차 군집으로 묶거나, 불확실로 남깁니다. 기존 2차 군집끼리는 자동 병합하지 않습니다. 이번 시험 기본값은 최근 원문 4,000개 검색·요청 최대 5회이므로 한 작업에서 약 1,000개의 1차 군집을 처리합니다. 요청 문자 상한에 걸리면 실제 배치 수는 200개보다 작아질 수 있습니다.

수동 실행은 별도 백그라운드 프로세스로 시작됩니다. 후보 읽기와 각 배치 저장 구간에서만 DuckDB를 짧게 연결하고 Gemini 요청과 점수 계산 중에는 유지하지 않습니다. 별도 `trend_clustering.lock`으로 중복 군집 작업을 막으며 같은 시간에 다른 Streamlit 메뉴와 수집 조회가 DB 연결 때문에 장시간 막히지 않도록 합니다.

처리 상태는 `trend_cluster_processing`에 저장합니다. 불확실·응답 누락 후보는 두 번 재시도하고 세 번째에도 확정되지 않으면 `needs_review`로 전환합니다. API 키가 없거나 전체 호출이 실패하면 정상 AI 경로의 유사도 의미 군집은 실행하지 않습니다. 대신 오프라인 순위 기능을 보존하기 위해 분리된 비상 결정론적 폴백으로 표시용 군집을 계산하되, `trend_cluster_processing`을 완료 처리하지 않아 이후 Gemini 실행에서 다시 검토합니다. 배치별로 검색한 미처리 원문, URL 중복 절감, URL 충돌 분리, 동일 제목 병합, 실제 요청한 1차 군집, 다음 배치 대기, 기존 군집 연결, 새 군집, 불확실, 충돌 차단, 입력·출력·사고·전체 토큰과 처리 시간을 `trend_clustering_jobs`와 `trend_clustering_job_batches`에서 확인할 수 있습니다. 화면은 완료된 1차 군집 수를 기준으로 1,000개당 예상 토큰도 계산합니다.

사용자가 저장한 `topics`, 자료팩, AI 요청서·응답, 초안, 리비전, 사실 확인과 발행 기록은 자동으로 수정하지 않습니다.
